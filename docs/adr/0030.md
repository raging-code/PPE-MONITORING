# ADR 0030: Effect-to-row mapping (P24-3a) and the split of P24-3

Status: Proposed (decided in the P24-3 session; confirm at the next design review).
Design: Rev 3.45 is frozen. Nothing in the frame, the migration, `constants.json` or the settings keys changes.

- **Split of P24-3 (decision).** P24-3 is three stages, not one: **P24-3a** (this one) the mapping of `step()` effects to alert, episode and audit rows, with `Ingest.tick()` and `Ingest.operator()`; **P24-3b** the real Source and Port behind the API (snapshot, WebSocket messages built from the effects and the committed ids, `unpersisted`, `event_seq` for audit rows, Acknowledge, Resolve, session start and end through the port); **P24-3c** steps 8 to 10 (DBWriter, SerialReader, SerialWriter and AudioThread wiring, the open alerts, Uvicorn, the 1 Hz tick, the pre-replay queue). P24-4 (doctor, `fw_version`) and P24-5 (supervisor, `cli ack`) are unchanged.
- **Where.** `effect_stmts()` and the two methods are in `io/ingest.py`, whose header already reserved this work; design 14.5 names no mapping module. `io/db_writer.py` gets one line: a committed unit keeps the ids of its tagged rows in `unit._ids` (the fallback path already did).
- **Same unit.** The frame row and the rows of its effects commit in one unit (design 1, commit paragraph). A tick or an operator action makes a unit of its own; an operator unit is `durable` (synchronous=FULL). `alerts.frame_id` comes from `Ref('frame')`, so it is NULL for a tick or an operator unit.
- **Identity.** An alert row is found by the `event_seq` of the effect that raised it (unique over the whole database, so it also works for an alert carried into a later session). An episode is found by its node while it is OPEN or ACKNOWLEDGED (`idx_episodes_one_active`). The `alerts.episode_id` of a `man_down` or `mayday` row is the active episode of its node, read inside the same transaction, so an upgrade to MAYDAY links the new row to the same episode.
- **Rows.** `RaiseAlert` inserts (`authenticated` is 0 only for `unauth_alert`); `ClearAlert` sets `cleared_ts` and `cleared_event_seq`; `ChangeAlertLevel` updates level and reasons in place and clears the acknowledgement only on escalation; `AlertAcknowledged` sets the acknowledgement; `EpisodeOpened`, `EpisodeAcknowledged` and `EpisodeResolved` insert and update the episode; `EpisodeEscalated` updates `kind` and writes the `EPISODE_ESCALATED` audit row (session = the current session, operator NULL, reason `MAN_DOWN to MAYDAY`); `EpisodeLabelChanged` has no row (WebSocket only).
- **Decisions the design does not give (please confirm).**
  1. A one-shot notice is stored with `cleared_ts` = `raised_ts` and `cleared_event_seq` NULL; `v_full_log` then shows its cleared row at the raise `event_seq`.
  2. A level change takes a new `event_seq` from `step()`, but the table has no column for it, so that number is used up and left out of the database. `event_seq` stays strictly increasing; it is not gapless.
  3. The audit rows `ACK_ALERT`, `ACK_EPISODE` and `RESOLVE_EPISODE` stay with the REST routes (`port.audit`, P19), so they are not written here.
- **Cost.** Clearing, acknowledging and changing an alert look the row up by `event_seq`, which has no index without `session_id`; the `alerts` table is small in Tier 1, and a new index would need a migration, which is frozen.
- **Failure.** A row that fails a constraint is skipped and counted (Rev 3.36), the frame row still commits, and `unit.rejected` tells P24-3b to broadcast that alert as `unpersisted`.
