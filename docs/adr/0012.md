# ADR 0012: WebSocket hub (P20)

Status: Proposed (decided in the P20 session; confirm at the next design review).
Design: Rev 3.45 is frozen. Nothing in the frame, the migration, `constants.json` or `ws.schema.json` changes.

- **Seam:** `api/ws_hub.py` has a `Hub` and a `Source` protocol (`authenticate`, `audit`, `snapshot`, `client_dropped`). The host (P24) implements `Source`, calls `install(app, hub)` after `create_app`, and calls `hub.publish_reading`, `publish_alert`, `publish_episode`, `publish_link`, `publish_system` and `publish_advisory` on the event loop with the message body (no `v`, `srv_seq` or `srv_ts`). `snapshot()` returns every `SnapshotMsg` field except the envelope and `epoch`; the hub adds `epoch` (one UUID per `Hub`, so one per host start). `install` wraps the app lifespan: the tick loop starts with the app and `shutdown()` closes every socket with 1000. P24 may also call `hub.start()` earlier, because the 1 Hz timer also stamps watchdog liveness through the `on_tick` callback. `api_rest.py` is not touched.
- **Origin and token on a WebSocket:** the HTTP middleware does not see WebSockets, so `Hub.serve` applies `security.origin_ok` itself. The socket is accepted first and then closed with the code, because a browser sees 1006 for a refusal before accept. Order: Origin/Host (4403, audit `ORIGIN_REJECTED`), then the first message must be a valid `auth` within `ws_auth_timeout_s` (4401). A late, missing, malformed or wrong-token first message is 4401; an invalid token or a non-auth first message writes `LOGIN_REJECTED` like a REST 401, a plain timeout writes nothing.
- **After auth:** `hb` on `/ws` is accepted and counted (`connected_tabs()`: a `/ws` socket whose last `hb` is under 3 s old; no audio field). Any other or malformed message is ignored. Every 5th tick the hub checks each open socket's token again, off the event loop, and closes a disabled or rotated-out operator's socket with 4401 (the item ADR 0008 left to P20).
- **Per-connection queue and srv_seq:** each connection has a deque (`ws_send_queue_max`, 64) and a sender task. The sender assigns `srv_seq` and `srv_ts` when it sends, so a message removed from the queue never leaves a gap. The snapshot is built and queued with no await before the connection joins the broadcast, so it is always first and nothing can slip in before it. `/ws/tick` has no snapshot: its `srv_seq` starts at 0 on its first tick.
- **Coalescing (Proposed rule, the design says only that coalescing leaves no gap):** a `tick` replaces an older queued `tick`. When the queue is full, the oldest queued `reading` (of the same node if there is one) is dropped to make room. A queue with no `reading` to drop (full of alerts, episodes, links) means the client is too slow: it gets 4408 and `client_dropped`, and no safety message is ever dropped. A send that takes more than `ws_send_timeout_s` gives 4408 too. A client being dropped is offered nothing more, so `CLIENT_DROPPED` is written once.
- **unauth_alert repeats:** a repeat of an open, unacknowledged `unauth_alert` is sent at once if the last one for that `alert_id` was over 1 s ago, otherwise the newest is held and the 1 Hz loop sends it. A clear or an Acknowledge is always sent at once and discards a held repeat. Every other alert message (raise, clear, level change, Acknowledge, one per linked alert of an episode Acknowledge) is sent at once; the host decides what to publish, the hub does not look inside.
- **Tick:** one timer for both sockets at `tick_s` (1 s, default), scheduled from a fixed start so one slow turn does not shift the next. It only enqueues, so a frozen client cannot delay it.
- **Not done here:** the real `Source` and the engine-to-hub wiring (P24); the dashboard client (P22); `/ws` is not in the REST endpoint table test.
