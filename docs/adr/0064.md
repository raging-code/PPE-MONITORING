# ADR 0064: Live speed control of a REPLAY host, host side (S7-7a)

Status: Proposed (confirm at the next design review). Decisions A to E below were taken by the author of the part; ADR 0061 decision D had left the speed control to a separate part.
Design: Rev 3.45 stays frozen; the change is an addendum at the end of `docs/design/s03-8.md` (REPLAY speed addendum), in the style of ADR 0061. This part is the host only. The dashboard control is S7-7b.

- **What.** One new endpoint, `POST /api/replay/speed`, body `{speed: 1|4|16}`, answer `{speed, paused, finished}`. It sets the speed, it does not step up or down, so a retry or a second open tab changes nothing more. The endpoint table goes from 14 to 15. The three values are `replay.SPEEDS`, the same three the command line takes (`--speed`); the request model and a test keep the two lists equal.
- **How the clock changes speed.** `ScaledClock.set_speed(speed)` re-bases the clock under its lock: the scaled time so far is kept (the old speed is applied to the time since the last reference), the base reference moves to now, and only then does the new speed count. `mono_ms` and `wall_ms` therefore never step and never run backwards, the next stored item is still due at the same source time, and every host timer (15 s and 60 s link loss, 30 s stillness, 10 s CO hysteresis, 120 s heat, the dedup window) goes on from where it was at the new rate. A paused clock only takes the new value and counts it from the next resume. The OS watchdog and the liveness stamps keep the real clock (ADR 0059), so a speed change cannot make the host look stalled.
- **Answers.** 200 `{speed, paused, finished}`. 401/403 as for every operator call. 409 `RECOVERING` (with `retry_after_s`) before the replay has started. 409 `STATE_CONFLICT` on a host that is not in mode REPLAY, and on a replay that has finished. 422 for any body whose `speed` is not the whole number 1, 4 or 16 (2, 0, 32, -4, `"4"`, `4.0`, `true`, `null` and a missing key are refused; the body refuses extra keys). No new error code.
- **Audit.** Migration 0005 adds `REPLAY_SPEED` to `audit_actions` (24 rows; no table changes). The route writes one row when the speed changed, with the operator, in the REPLAY session of the test database and the reason `1x to 4x` (before and after, so the event log and the CSV show it). Asking for the speed the replay already has changes nothing and writes no row.
- **Wire.** Nothing new: `replay.speed` already exists in the snapshot and the system message (ADR 0061). `Wire.on_replay_changed` sends the system message at once, so other open screens follow within one message; a page reload gets the new speed in the snapshot.
- **Port.** `Port.replay_set_speed(speed) -> ReplaySpeedState(speed, previous, paused, finished, changed)`, implemented by `HostPort` (it does not block, so the route calls it on the event loop like `replay_set_paused`). `ReplayThread.set_speed` refuses a value outside `SPEEDS` (and `True`) and does nothing on a finished replay.
- **Decisions to confirm.** (A) One state-setting endpoint, separate from pause (a body with both keys is a 422 on each route). (B) Only 1, 4 and 16, as at the command line, not a free number. (C) A speed may be set while the replay is paused; it counts from the resume. (D) Any logged-in operator may change it, as for pause. (E) One audit row per change with both speeds in the reason.
- **Known effect, unchanged from ADR 0059.** The host evaluates silence rules on the 1 Hz tick, which is real time, so at 16x a silence rule can fire up to 16 source seconds after its limit. A change of speed does not make this better or worse than starting at that speed.
- **Tests (development sandbox, Linux).** `test_replay_speed.py`: clock re-base with a fake clock (no jump, no step back, paused, repeat, bad values), the thread, the route with a fake port (rows, repeats, 409, 401/403, 11 bad bodies), `HostPort`, the wire, migration 0005 (fresh and upgraded from version 4), and a real REPLAY host whose speed is changed through the real route while it runs and while it is paused (the replay clock does not step at the change, 500 ms of real time are then 8 s of source time at 16x and 2 s at 4x, a repeat sends no message and writes no row, the end of the data and the refusal after it, three audit rows). Existing tests that listed the migrations, the audit action count (23 to 24) or the 14 endpoints were updated.
- **Not here.** The dashboard control and the mock host (S7-7b). A run on Windows. A speed of 0 or a free value. Speed for LIVE or SIMULATOR (refused with STATE_CONFLICT).
