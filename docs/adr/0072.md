# ADR 0072: confirm who wears each jacket before Start monitoring, and set a firefighter inactive (S8-3a host, S8-3b dashboard)

Status: Proposed (decided with the operator on 2026-11-28; confirm at the next design review).

Design: Rev 3.45 stays frozen. This ADR adds one endpoint to the REST list of design 3.8 (18 to 19) and one audit action (Migration 0007, audit_actions 27 to 28). No wire message, no setting and no new error code.

## Why

ADR 0070 and 0071 stored who wears which jacket, with history, so a stored reading can be joined to a firefighter by node and time. That join is only right if the assignment is right. An assignment made on one day stays open until someone changes it, so on the next shift the readings of a different person could be stored against yesterday's firefighter, and nothing asked. A person who left the department also stayed in the pick list, with no way to remove them.

## Decisions

- **A. A jacket check before Start monitoring (dashboard only).** While the siren is locked, the sound bar shows 'Who wears each jacket today?': one selection per active roster node, started at what the host has (Nobody when none), and one button 'Confirm who wears the jackets'. Start monitoring stays off, with the line 'Confirm who wears the jackets first.', until the check is confirmed. The browser siren and the host alarm do not depend on it in any other way.
- **B. What Confirm does.** It sends the changes through the existing `POST /api/firefighters/assign` in two phases: first every jacket that changes hands is ended (firefighter_id null), then the new wearers are put on. Two people can therefore swap nodes without the host refusing one of them. The list is read again after the last call. A refusal shows its sentence and confirms nothing. Nothing is sent when nothing changed.
- **C. The confirmation lapses when anyone changes who wears what.** The page keeps the node-to-firefighter pairs it confirmed. The 30 s read of the list (WearerSync) or a change in Settings that makes them differ switches the check back on; putting them back switches it off again. Log out forgets the check.
- **D. It never blocks when the host cannot say.** If the list did not arrive (host down, an old host, the e2e mock host) or the host has no active firefighter, Start monitoring is not held back. With no firefighter at all the bar says 'No firefighters are set up, so the readings are not linked to a person. Add one in Settings.' A host that is down must never keep the operator from starting the browser siren.
- **E. Alias only.** The picker shows FFR-NN, not the name (ADR 0071 D: the name is on the Settings screen only). The operator reads the name-to-alias list in Settings. Option: show the name here too if the data-governance owner agrees.
- **F. Set a firefighter inactive or active again.** `POST /api/firefighters/active` {firefighter_id, active} -> {firefighter_id, alias, active, result}. Setting inactive also ends the jacket the firefighter wears; an inactive firefighter cannot be assigned (the rule of ADR 0070 D, now with a way to reach it). Nothing is deleted: the profile, the consent record and the assignment history stay, so earlier readings still join to the right person. Same checks as the other writes: 404 for an unknown id, 409 RECOVERING, 422 for a wrong type, 401/403. A repeat of the state it already has writes no row. One audit row, `FIREFIGHTER_ACTIVE_SET`, with the operator and the reason `firefighter_id 3 (FFR-03) inactive`, never the name. `services/firefighters.plan_set_active` plans it; `HostPort.set_firefighter_active` queues it through the writer like the other firefighter writes.
- **G. Settings.** The firefighter list has a Status column with 'Set inactive' or 'Set active' for each row and one sentence of result.

## Not here (open points)

- **End shift does not end the assignments.** A new session after End shift keeps the same wearers. The check of decision A runs at Start monitoring, which is once per browser page, so a second shift run from the same page without a reload is not asked again. Ending the assignments in the End shift transaction would change `close_session` (design 2.11) and is not done here.
- **The readings of one firefighter are not exported yet.** The CSV (v_full_log) is frozen and carries no firefighter column. A stored frame joins to the firefighter by node and time (`firefighter_assignments`); an export or view that does the join for the forecasting work is a separate part.
- Editing a profile (weight, age and heart rate change over time) and withdrawing consent have no route yet; a wrong value is still corrected by direct database access, which is an audit gap.
- Any logged-in operator may set a firefighter inactive, like every other route; an admin role is a question for the data-governance owner.
- There is no CLI command for set-inactive (the REST route is the only way).
