# ADR 0071: the Settings screen and its endpoints for firefighter profiles (S8-2a host REST, S8-2b dashboard)

Status: Proposed (decided with the operator on 2026-11-28; confirm at the next design review).

Design: Rev 3.45 stays frozen. This ADR adds three endpoints to the REST list of design 3.8 (15 to 18), as ADR 0070 said it would. No migration (Migration 0006 already has the tables), no new error code, no new WebSocket message and no setting.

## Why

ADR 0070 added firefighter profiles, consent and node assignment on the command line. The operator wants to add a firefighter and change who wears the jacket from the dashboard, and to keep the real name off the command line and out of the shell history.

## Decisions

- **A. Three endpoints.** `GET /api/firefighters` (the list, with names, for the Settings screen), `POST /api/firefighters` (add a profile with its consent record) and `POST /api/firefighters/assign` (put a firefighter on a node, replace, or end with `firefighter_id` null). Each is documented in docs/design/s03-8.md (FIREFIGHTER addendum) and listed in the endpoint-table test.
- **B. One set of checks.** `services/firefighters.py` holds `check_profile` and `plan_assign`; the CLI and the routes both use them, so the ranges, the consent rule and the refusal sentences are the same on both. `FirefighterError.kind` ('invalid', 'missing', 'conflict') maps to 422, 404 and 409.
- **C. The writer owns the writes.** `HostPort.add_firefighter` and `assign_firefighter` plan the rows and queue them through `Ingest.write` as one durable unit, the way the PIN login does; the route waits for the commit. A lock makes the id read and the write one step. The audit row is written by the route with the operator.
- **D. Names.** The name travels only in the add request and in the `GET /api/firefighters` answer. The audit reasons carry the id and the alias (`firefighter_id 3 (FFR-03)`), a refusal message never holds a name, and the 422 handler echoes no submitted value. The list is not audited, like GET /api/events. Any logged-in operator may read it; the dashboard shows the name on the Settings screen only.
- **E. The wearer on the card comes from the list.** The node card shows the alias from `GET /api/firefighters`, not from the wire, so no snapshot field and no generated file changes. A change made on another screen shows after the next read of the list (the Settings screen reloads it after every change).
- **F. Writes wait while the host recovers** (409 RECOVERING), like Start and End shift. A read does not.
- **G. Same permission as the other routes.** Any logged-in operator may add a firefighter and change an assignment. A separate admin role is not built.

## Dashboard (S8-2b)

- **H. Settings button.** The top strip has a Settings button next to Sessions. It opens a panel in normal flow (like the Sessions list, scrolling inside itself) with three parts: the firefighter list (alias, name, age, weight, resting heart rate, smoker, the jacket worn), 'Who wears the jacket' (one selection and one Save per active roster node; Nobody ends the assignment) and a button 'Add firefighter' that shows the form.
- **I. The form.** Full name, age, height, weight, resting heart rate, smoker (required), maximum heart rate, sex and years of service (optional), and a Consent group: the consent tick, the form version, the witness name and the consent date (today by default, not in the future). The page checks the ranges to save a round trip and shows the first problem as one sentence; the host decides. Nothing is sent without the consent tick. On success the panel says 'Saved as FFR-02.' and reloads the list.
- **J. The alias on the card.** A node card, and the grey never-heard card, show 'Worn by FFR-01' when the host reports a firefighter on that node. `WearerSync` (mounted by App only, so Shell and its tests send nothing new) reads the list when the screen turns live and every 30 s, and the Settings screen refreshes it after every change. The store holds the alias only, never a name.
- **K. Not built in the dashboard.** Switching a roster node on or off (CLI), editing a profile, setting a firefighter inactive, withdrawing consent.

## Not here (open points)

- Editing a profile, setting a firefighter inactive and withdrawing consent have no route yet (a gap since ADR 0070; the audit gap stays until they exist).
- Switching a roster node on or off stays a CLI command, because the host reads the roster at start-up.
- The dashboard half (decisions H to K above) is part S8-2b, built after the host half. Its tests were written without a Node install, so they count as unrun until `npm test` has passed on the operator laptop.
- The names are shown to any logged-in operator on the Settings screen; whether that needs an admin role is a question for the data-governance owner.
