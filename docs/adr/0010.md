# ADR 0010: sessions list and dashboard outage report (P19c-1)

Status: Proposed (decided in the P19c-1 session; confirm at the next design review).
Design: Rev 3.45 is frozen. Nothing in the frame, the migration or `constants.json` changes.

- **No new Port method.** `GET /api/sessions` is a read-only query in a worker thread, like `GET /api/events` (no audit row). `POST /api/dashboard-outage` validates and calls `port.audit('DASHBOARD_OUTAGE', ...)`. Both read the clock through `api_rest._now_ms`, which tests replace.
- **Session row (3.8 lists the fields, not their meaning):** `alert_count` counts every `alerts` row of the session, notices included. `unresolved_episodes` counts episodes of that session whose state is not RESOLVED, so an episode carried over by End shift still counts against the session that opened it. `duration_s` is `(ended_ts - started_ts) / 1000`, and for the open session it runs to now. Rows are newest first. `limit` defaults to 50 and is 1 to 500 (3.8 gives only the default; the upper bound is a proposal).
- **`highest_level_by_node`:** a map from node id (a string, as JSON keys are) to `WARNING` or `DANGER`, taken from the `alerts` rows of the session. A node whose alerts are all level NONE (notices), and an alert with no node, are left out; the dashboard reads an absent node as NORMAL. Frames are not scanned, because that would make the call slow on a 24 h database (the design asks for under 500 ms of liveness movement).
- **Outage times are UTC milliseconds,** like every stored timestamp, and `duration_s` is seconds, so the 1 s tolerance is 1000 ms. P22c must send `Date.now()` values. If the dashboard were to send seconds the check would refuse every report with 422, which is loud rather than silent.
- **Check order and audit:** the four rules of 3.8 all give 422 `VALIDATION_ERROR`. A refused report writes no audit row (`audit_actions` has no rejection action for it, as in ADR 0007). `duration_s` may not be NaN or infinite. The `DASHBOARD_OUTAGE` row carries `started_ts`, `ended_ts` and `duration_s` in `reason`, because `audit_events` has no columns for them.
- **Left for P24:** the "moves no liveness stamp by more than 500 ms" check needs the running host. The route-level test here only shows that the query runs off the event loop, never touches `frames` (query plan) and takes under 500 ms on 30,000 frame rows.
