# ADR 0056: PIN login, login sessions and "remember me" (Part 28)

Status: Decided (the four decisions below were confirmed by the project owner in design-review preparation, 2026-11-28; P28-3 and P28-4a were built on them).
Design: Rev 3.45 (the .docx) stays frozen. This ADR is a deliberate change to design 4 (operators and security), 3.8 (login endpoint, close codes) and 2.3 (audit actions, operators). The Markdown extracts in docs/design are updated by P28-1; fold the change into the next design revision. Nothing is built by this ADR: P28-2 adds Migration 0003, P28-3 to P28-6 add the code.

- **Problem.** The dashboard asks for the 32-character operator token on every new tab or browser start (sessionStorage, by design). Nobody can memorize it, and copying it each time is slow during a shift.
- **Decision.** A second login form: display name + PIN. A correct PIN returns a random session token with an expiry. The browser keeps that token in sessionStorage (default) or localStorage ("remember me" ticked). The operator token stays as the admin and break-glass login, with no expiry and no lockout.
- **Decision 1, session lifetime.** 12 hours, settings key `session_hours` (default 12, allowed above 0 up to 168; P28-4b built the wider range and P28-6 corrected this line to match it). The same expiry with or without "remember me".
- **Decision 2, PIN.** Digits only, 6 to 12 of them. Stored only as a salted scrypt hash (hashlib.scrypt, n=16384, r=8, p=1, 16-byte random salt per operator) in `operators.pin_hash` and `pin_salt`, compared with hmac.compare_digest. Never in the browser, logs, CSV, audit rows or settings. A login for an unknown name, a wrong PIN, an operator without a PIN and a disabled operator all give the same 401, and the unknown-name case still spends a scrypt verification, so the answer does not reveal which names exist.
- **Decision 3, failed PINs and the s04 rule.** Design 4 says a lockout must not blind the incident commander. So: the answer carries `retry_after_s` from the same global backoff as today (1 s doubling to a cap of 5 s, one counter for every login form, so it says nothing about which names exist); per operator, `pin_fails` counts consecutive failures; after 5 consecutive failures `pin_locked_until` is set 15 minutes ahead and LOGIN_LOCKED is written once; the lock clears itself and a correct PIN resets the count. The lock applies to the PIN form only: the operator token is never locked, so the commander always has a way in. The host listens on 127.0.0.1 only, so only someone on the station can try PINs.
- **Decision 4, remember me.** Off by default and chosen by the operator at each login. The host stores the choice in `login_sessions.remember` (audit only); the browser decides the storage. Log out revokes the session on the host and clears both storages.
- **Session token.** secrets.token_urlsafe(24), stored as the HMAC-SHA256 with server_salt (the rule of 4.1) in `login_sessions.token_hash`, with created_ts, expires_ts and revoked_ts. The table is called login_sessions because `sessions` already means a monitoring shift.
- **Authentication.** `authenticate()` accepts an operator token (as today) or a session token whose row is not revoked, not expired and whose operator has active = 1. Every call reads the database, as today. Disabling an operator, rotating its token and setting a new PIN revoke all of its sessions at once.
- **Wire.** POST /api/login keeps the {token} form and gains {display_name, pin, remember}; new POST /api/logout. The WebSocket auth frame and the Authorization header carry a session token exactly like a token. An expired or revoked session closes the socket with 4401, as today. No new error code, no new WS message, no change to the 4401 rule.
- **Audit.** Migration 0003 adds PIN_SET (CLI, session_id NULL), LOGOUT and LOGIN_LOCKED to audit_actions (18 to 21). LOGIN_OK and LOGIN_REJECTED are reused for the PIN form, with the reason `pin` or `token`.
- **CLI.** `set-pin --operator-id N` reads the PIN twice with getpass (no --pin argument, so it never reaches a shell history), never prints it and never logs it. create-operator is unchanged and still issues the long token.
- **Risk.** On a shared station, "remember me" means whoever uses that browser acts as that operator, and audit_events names that operator. Mitigations: off by default, 12 hours, Log out at shift change, and a `cli doctor` row for operators without a PIN (P28-6). Expired rows are kept for the audit trail; a purge is left open.
- **Parts.** P28-1 docs and this ADR. P28-2 Migration 0003 (operators gains pin_hash, pin_salt, pin_fails, pin_locked_until, pin_set_ts; table login_sessions; three audit actions). P28-3 PIN and session logic in api/security.py. P28-4 endpoints and the set-pin CLI. P28-5 dashboard login screen, storage choice, Log out. P28-6 Playwright test, doctor row, close-out.
- **Progress.** P28-1, P28-2, P28-3 and P28-4a done (Migration 0003; PIN and session logic; the PIN form of POST /api/login and POST /api/logout through the host port). P28-4b (CLI set-pin, the session_hours setting, revoke on rotate and disable), P28-5 (the dashboard login screen, the storage choice, Log out) and P28-6 (Playwright PIN test, doctor row, close-out) are done too: all six parts are built. - **P28-3 notes.** The write side is host/ppe_host/api/pin_auth.py (set_pin, pin_login, create_session, revoke_session, revoke_operator_sessions): plain functions on a writable connection, no audit rows (the P28-4 route writes them through the port). Hashing, the PIN rule and the session check are in api/security.py. The scrypt check runs outside the write transaction. The lock resets pin_fails to 0 when it starts; a wrong PIN of a disabled operator or of an operator without a PIN is not counted. The session_hours setting is added in P28-4 with the wiring; until then security.DEFAULT_SESSION_HOURS (12) is the value, and Authenticator takes an optional now_ms clock.
- **Checked here.** Nothing is run: this part changes Markdown only.
- **Open, please confirm.** (1) 12 hours. (2) 6 to 12 digits. (3) The self-clearing 15-minute lock with the operator token as break-glass. (4) Remember me off by default.
- **P28-4a notes.** POST /api/login takes {token} or {display_name, pin, remember} (exactly one form; a mix or a missing field is 422 and never echoes the PIN). The PIN form answers {operator_id, display_name, session_id, session_token, expires_ts}; the token form is unchanged. POST /api/logout is the thirteenth listed endpoint and answers {logged_out}. The Port gains pin_login, start_login_session and logout; they block (scrypt, the commit wait), so the routes call them in a worker thread, and HostPort sends the planned statements through Ingest.write as durable units that are committed before the answer: a failure count or a lock survives a restart, and a session is readable by the next request. api/pin_auth.py is now a set of planners (plan_login, plan_set_pin, plan_session, revoke_stmt) plus the same conn functions as before, so the host and the offline CLI share one decision. The failure count and lock are one atomic UPDATE. A locked operator answers 401 at once with retry_after_s = seconds left and no growing delay (no scrypt is run); every other failure is the same 401 'invalid name or PIN' with the global delay. LOGIN_LOCKED is written once, on the failure that starts the lock; LOGIN_REJECTED and LOGIN_OK carry reason pin. HostPort builds its Authenticator with the host clock, so a session expires by the same clock that created it. Session length is still security.DEFAULT_SESSION_HOURS (12): the setting is P28-4b.
- **P28-4b notes.** `cli set-pin --operator-id N` gives the operator a random PIN (--length 6 to 12 digits, 6 by default) that is printed once; --prompt reads a typed PIN twice with getpass instead. A PIN is never an argument, so it is not in a shell history. Only the scrypt hash and salt are stored. It clears the failure count and the 15-minute lock (this is how an administrator unlocks an operator before the lock runs out), ends that operator's login sessions, refuses a disabled operator, and writes PIN_SET offline (session_id NULL, event_seq 0). rotate-token and disable-operator now also revoke the operator's login sessions in the same transaction (rotate-token prints how many ended, before the TOKEN line). The setting session_hours (default 12, above 0 and at most 168, checked when the settings load) sets the session length; it is in HASH_EXCLUDED, so changing it does not end a shift. It lives in host/config/settings.json and s01-settings.md; the design docx is not touched. HostPort reads it for every new session; sessions already made keep their own expiry.
- **P28-5 notes.** The dashboard Login page opens on name and PIN (the PIN field is a password field and is emptied after every attempt; Sign in stays off until there is a name and 6 to 12 digits), with a "Remember me on this browser" box that is off by default and a link "Use the admin token instead" to the old token form (and back). The host's session token is kept in the same slot as the operator token (`ppe_token`), in sessionStorage, or in localStorage when the box is ticked (if the browser blocks localStorage the token stays in the tab). Everything that sends a token (REST, /ws, the Web Worker's /ws/tick) reads that one slot through `store/token.ts`, so none of it changed. A 401 with retry_after_s of 60 s or more is the lock and says so in minutes and points to the admin token. Log out (top strip, asks once because the screen stops monitoring) calls POST /api/logout with the stored token, best effort, then clears both storages, stops the sockets and shows Login, also when the host is down. Close code 4401 now clears both storages, and a 401 on any logged-in REST call (`api/authfetch.ts`) does the same, so a session that ends in an open tab shows Login on the next call instead of a silent failure. The Playwright helper opens the admin token form first; a PIN end-to-end test with a mock host PIN login is P28-6.
- **P28-6 notes.** The mock host (e2e/mock_host.mjs) now speaks the PIN form and POST /api/logout: name Ana with PIN 482913 gives the session token e2e-session-token; a wrong PIN is a 401 with retry_after_s 1; the 5th wrong PIN in a row is a 401 with retry_after_s 900 and locks the PIN form (even the right PIN) while the admin token e2e-token still gets in; Log out revokes the session token; `/__ctl {"expire":true}` ends the session on the host and closes its sockets with 4401. The spec e2e/tests/pin_login.spec.ts has six tests: sign in and a wrong PIN (field emptied, session storage only, remember off), Remember me (a new tab is signed in with it and shows Login without it), Log out (asks once, the host refuses the old token, both storages empty, a new tab shows Login), a session that ends on the host (4401, Login), the 15-minute lock with the admin token as the way in, and the token sign-in of the other specs. helpers.ts gains signInWithPin and storedTokens. host/tests/test_e2e_config.py checks that the mock host's PIN answer is one PinLoginResp accepts, that its request is one LoginReq accepts, that helpers.ts and the mock host agree on the name, PIN and session token, and that the spec covers the PIN login. cli doctor has one more row, `operator PINs` (14 rows on a good machine): it names the active operators without a PIN and is a PASS, never a FAIL, because the operator token stays a valid login; it is a SKIP without a database, without an active operator or before migration 0003. The session_hours range in Decision 1 now says what was built (above 0 up to 168). The mock host answers a wrong PIN at once and does not wait out the delay of the real host; the lock, the storage choice and the screens are the real dashboard in Chromium, the delay is covered by pytest. NOT run in a browser in the development sandbox: the first `just test-e2e` on your machine is the first real run.

- **P28-7 notes.** Two follow-ups from the open list of P28-6. (1) `cli doctor` has a fourth status, WARN. The operator PINs row is a WARN (not a PASS) when an active operator has no PIN; the summary line gets ", N warned" only when something warned, so a run with no WARN prints the same line as before, and a WARN never changes the exit code (0 unless a check failed). (2) `cli purge-login-sessions [--older-than-days N] [--dry-run]` (services/login_purge.py): deletes login_sessions rows that have been dead for MORE than N days (default 30); a session is dead from the earlier of its revoked_ts and its expires_ts, and a live session is never deleted, even with N = 0. Offline only (refused while the host lockfile is live, like purge-session), exit 0 or 1. No audit row: audit_actions is frozen at 21 and nothing else points at a login_sessions row, so only that table changes; the command prints the count. Backup copies keep the rows they were made with. Not built: a scheduled purge, a purge on End shift, an audit action for it (needs a migration).\n

## Review decision (2026-11-28)

Decisions 1 to 4 are confirmed as written: 12 hours with the `session_hours` setting, a 6 to 12 digit PIN stored as a salted scrypt hash, a 15-minute lock after 5 consecutive failures on the PIN form only (the operator token is never locked, so the incident commander is never blind), and "remember me" off by default. The remaining parts (P28-4b onward) go ahead on these. Changing any of them later would need a new migration.
