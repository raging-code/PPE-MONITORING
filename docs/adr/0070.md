# ADR 0070: one prototype on the dashboard, and firefighter profiles with consent (S8-1, host and CLI)

Status: Proposed (decided with the operator on 2026-11-28; confirm at the next design review).

Design: Rev 3.45 stays frozen. This ADR is a deliberate change to design 2.1 (aliases, never names) and adds a table group to design 2.3. No wire message, no REST endpoint and no setting changes: S8-2 (the Settings screen, which needs new endpoints and a wire flag) is a separate part.

## Why

The trial uses one prototype jacket. The roster of three nodes (ADR 0028) and the three-node SIMULATOR scenarios made the dashboard show three responders. The operator also needs to know who is wearing the PPE, and the profile of each firefighter (age, height, weight, resting heart rate, smoker) is wanted for the later forecasting work.

## Decisions

- **A. One prototype for now.** The roster table keeps nodes 1 to 3 (its CHECK is unchanged; more nodes are a design change). `cli set-roster --node N --active 0|1` switches a node on or off. The host reads active nodes at start-up, and the dashboard already lists only `active` roster rows (LiveScreen), so switching nodes 2 and 3 off gives a one-responder dashboard with no dashboard change. The last active node cannot be switched off. Switching a node off ends its assignment. The change is an audit row, `ROSTER_ACTIVE_SET`.
- **B. Firefighter profile.** Table `firefighters`: alias `FFR-NN` (from the id), full name, sex (optional), age, height, weight, resting heart rate, maximum heart rate (optional, above resting), smoker, years of service (optional), the consent record, active, created time. Ranges are CHECK constraints and are also checked in `services/firefighters.py`. sex, maximum heart rate and years of service were added to the operator's list because they are the usual inputs of a heart-rate or heat-strain model; medical notes were left out on purpose (the most sensitive field, and the data-governance fields are not filled in yet).
- **C. Consent is part of the profile.** A profile cannot be saved without `--consent`, a consent form version, a witness and a date (default today, not in the future). The signed paper stays outside the repository; the database holds only that consent was recorded, when, on which form version and who witnessed it.
- **D. Who wears which jacket.** Table `firefighter_assignments` (node, firefighter, start, end). At most one open assignment per node and per firefighter (partial unique indexes). `assign-firefighter --node N --firefighter-id F` replaces whoever wore the node; leaving out `--firefighter-id` ends it. History is kept, so a stored frame can be joined to the firefighter by node and time. Audit row `FIREFIGHTER_ASSIGNED`.
- **E. Names.** The real name is stored (the operator's decision) but shown only by `cli list-firefighters --show-names` and, in S8-2, the Settings screen. The dashboard, the wire, the audit log (reason text is the id and alias only), the logs and the CSV exports carry the alias only. Nothing deletes a firefighter row; a person who leaves is set inactive (no command yet, see open points).
- **F. Simulator.** The SimulatorThread takes the active roster as its nodes, so a one-node roster makes traffic for that node only. A new scenario `single` runs the three events one after the other on one node: CO ramp from 0 s, man-down from 150 s, link loss from 260 s. Start it with `python -m ppe_host.main --mode SIMULATOR --scenario single`. The default scenario `rehearsal` is unchanged (with one active node it only shows the CO ramp).
- **Migration 0006** adds the two tables, three indexes and the audit actions `FIREFIGHTER_ADDED`, `FIREFIGHTER_ASSIGNED`, `ROSTER_ACTIVE_SET` (audit_actions 24 to 27).

## Deviation from the earlier governance rule

design 2.1 and docs/data-governance.md said no responder name is stored anywhere in the software. That is no longer true: `firefighters.full_name` is personal data, and so are the profile numbers once linked to a name. docs/data-governance.md is amended in the same part. The software does not encrypt the column; the drive encryption of rule 4 is what protects it, and a backup or export of the database contains it. The data-governance fields marked [FILL IN] must be completed before the first real firefighter is added.

## Not here (open points)

- S8-2: the Settings button and the Add firefighter form in the dashboard, the REST endpoints and the wire change they need (the endpoint table is frozen and its tests list it).
- Editing a profile (weight changes), setting a firefighter inactive, and withdrawing consent have no command yet. Until they exist, a wrong entry is corrected by an operator with direct database access, which is an audit gap to close in S8-2.
- With the CLI, the name is typed on the command line and stays in the shell history. The S8-2 form removes that.
- The forecasting use of the profile numbers is not built and not decided here.

## Tests

`host/tests/test_firefighters.py`: migration 0006 objects and audit actions; add with consent and every refusal; the audit rows contain no name; assignment replace, same-person no-op, one node per firefighter, end; roster switch with its two refusals; the CLI commands and `--show-names`; the `single` scenario and the simulator following a one-node roster.
