# ADR 0040: second-drive copy, read-only backups and the integrity check at session end (P26-3)

Status: Proposed (decided in the P26 sessions; confirm at the next design review).
Design: Rev 3.45 is frozen (2.5 integrity check and online backup, 2.6 backup and restore, 2.8 deletion, 3.8 `POST /api/session/end`). Nothing in the migration, `constants.json`, `alert_catalog.json`, the frame, `api/models.py` or the REST list changes. One host-only setting is added (below).

- **Where it runs.** All of it is in `HostPort.end_session`, after the End shift unit has committed, in the worker thread of the route, so the event loop never waits for a disk. Order: online backup and its verification (as before), the copy to the second drive, then the full `integrity_check` of the live database. Each step has its own system row in the new session; a failure of one never undoes the shift or skips the next step.
- **New setting `second_drive_dir`** (host-only, default `""` = no copy). It is a path key (resolved against PPE_HOME; an absolute path such as `E:/ppe-backups` stays as it is) and is in `HASH_EXCLUDED` like the other path keys, so plugging the USB drive in at another letter does not end a shift as CONFIG_CHANGED. `test_settings.py` now counts 17 excluded keys, not 16, and `test_settings.py` and `test_gen_constants.py` count 36 settings keys, not 35: the key count is a frozen gate, so this is a design decision to confirm, not a detail. The design names the second drive (2.6 step 2) but no setting for its place; the row for `docs/design/s01-settings.md` is not edited here (Rev 3.45 is frozen) and needs a design line.
- **The copy.** `io/backup.copy_to_second_drive` copies the verified local backup file (a plain file copy is safe here: the backup is closed, has no WAL and is read-only, which is why `online_backup` used the backup API for the live file but this step does not). The folder must already exist: a drive that is not plugged in fails the copy; it never creates a folder on the system disk. The folder may not be `backup_dir` itself (that is not a second copy). The file is written as `<name>.part`, renamed into place, made read-only, and checked with `verify_backup` (open read-only, `integrity_check`, schema, `foreign_key_check`); a copy that fails the check is deleted and reported. A read-only copy of the same name is replaced.
- **Rows.** The local backup keeps its row (`BACKUP_OK` with the file name, or `BACKUP_FAIL` with the reason). The second copy adds `BACKUP_OK` with detail `second drive: <path>` or `BACKUP_FAIL` with `second drive: <error>`. With a failed local backup the copy is not tried and its row says so. No new kind: the 29 kinds of `system_event_types` are unchanged.
- **`backup_ok`.** The `POST /api/session/end` answer carries one boolean. It is False when the local backup, its verification or the second copy failed, so a missing USB drive is shown to the operator the same way a failed local backup is. With `second_drive_dir` empty it means exactly what it meant before.
- **Read-only backups.** Already true since P11-2 (`online_backup` and the copy leave 0444, or the Windows read-only attribute); P26-3 adds the tests for the backup file, the copy and a re-written file, and `purge-session` (P26-2) already lifts and restores the attribute.
- **The integrity check.** `io/backup.integrity_check(path)` runs the full `PRAGMA integrity_check` on a read-only connection (readers do not block the WAL writer) and returns `(ok, detail)`; a file that cannot be read at all is `(False, 'DatabaseError: ...')`. `end_session` writes `INTEGRITY_OK` or `INTEGRITY_FAIL` with detail `integrity_check at session end: <ok | first three problems>`. It checks the live database, not only the backup: a backup is a page copy, so a bad live page would be copied into it, and `verify_backup` would still catch most of that, but the live result is what the operator needs.
- **The purge reaches the second drive.** `purge-session` now also sweeps `second_drive_dir` of the settings, in addition to `--usb-dir`. A drive that is configured but not plugged in is exit 2 with "does not exist (drive not connected?)", as for `--usb-dir`, so a purge is never reported complete while a copy of the session may still exist.
- **Measured (development sandbox, 24 h database of P25-4, 31 MB).** `integrity_check` 0.18 s, online backup 0.1 s, copy plus verification 0.19 s. Timing is machine-dependent, and a USB stick is slower than the sandbox disk; all three run in the worker thread, after the shift is already closed and committed.
- **Not done here.** An `INTEGRITY_FAIL` at session end is logged and shown in the log only: no banner and no change of state, because the design gives none for this event (the start-up one, H22, quarantines and restores; a live database cannot be quarantined mid-shift). The `integrity_check` that 2.5 also lists "after RECOVERING ends" exists since P25 (`recovery_run`). `CLEAN_SHUTDOWN` and `ABANDONED` closes make no backup: 2.5 says the backup runs at the end of each session, but the code since P25-3 backs up only at End shift, and 2.6 says the second copy is made "at End shift".
- **Open, please confirm.** (1) The name and default of `second_drive_dir` and that it needs a design line in `s01-settings.md`. (2) `backup_ok` is False when only the second copy failed. (3) An integrity failure does not change `backup_ok` and has no banner; a dashboard banner would need a design line. (4) Whether a clean shutdown or an abandoned session should also be backed up (2.5 reads "each session"). (5) The restore test before the first trial (2.6 step 1) is a manual check on the field laptop: `python -m ppe_host.cli backup-verify --file <file on the USB drive>`, then restore it by the start-up path.
