# ADR 0033: Link, system and advisory messages (P24-3b-2b) and what stays open

Status: Proposed (decided in the P24-3b-2b sessions; confirm at the next design review).
Design: Rev 3.45 is frozen. Nothing in the frame, the migration, `constants.json`, the settings keys or `api/models.py` changes.

- **Split of P24-3b-2b (done).** 2b-i `link` and `system` messages (`wire.py`, test_wire_2b1.py); 2b-ii advisory rows and the `advisory` message (`io/ingest.py`, `wire.py`, test_advisory_wire.py); 2b-iii this ADR and the doc touch-ups. P24-3c (steps 8 to 10) is unchanged.
- **Link messages.** `Wire.link_state(node)` is derived from the engine (`not_connected`, `ok`, `weak_signal`, `signal_lost`, `link_lost`, `recovered`). One `link` message goes out per change, not per frame, and the snapshot calls the same function, so a snapshot and the live messages cannot disagree. At `attach()` the current states are recorded as already known, so a start-up sends no message.
- **System messages.** The body is built from Health (base), the recovering flag, the session, and the banner sources. A new message is sent only when the body changes, except `rejected_frames`, which rides on the 1 Hz `Wire.tick()` only. `BANNER_ACK` goes out at once from `HostPort.ack_banner`, not on the next tick.
- **Hub methods are optional.** `publish_link`, `publish_system` and `publish_advisory` are called only when the hub has them, so an older hub or a test hub keeps working.
- **Advisory is off until a Wire turns it on (decision).** `Ingest.adv_cfg` is `None` by default and `advisory_step` is skipped while it is `None`. `Wire.enable_advisory(heartbeat_s)` forwards to `Ingest.enable_advisory`, which is idempotent; a second call replaces the config without resetting `AdvisoryState`. Nothing in the host calls it yet: P24-3c passes `advisory_heartbeat_s` from `settings.json` when it builds the host. The value 300 is still on the sign-off list (Coding Guide section 6).
- **Where the row is written.** `advisory_step` runs after `step()` on every `frame()` and `tick()` and its `AdvisoryRow` effects get one `advisory_summaries` row each, in the same unit as the frame or tick (so same commit, strict `event_seq` order). `source` is always `table` and `passage_ids` stays NULL in Tier 1.
- **No read-back.** Alerts and episodes are read back from their rows because the dashboard needs the database id. An advisory row has no id on the wire (3.8), so its message is built straight from the effect.
- **Known weak test.** `test_a_tick_also_runs_advisory_step_once_enabled` only asserts `>= n0`. A sharper check (advance the FakeClock past `advisory_heartbeat_s`, then expect a unit and exactly one new row) is left for P24-3c, when the real driver exists.
- **Still OPEN (unchanged from ADR 0032): `unpersisted`.** The wire still has no `unpersisted` field, and the interim rule of ADR 0032 (hold the message until the commit, send none for a rejected row) stays. The host alarm does not depend on it. It needs your decision (a) add the field and a provisional id, or (b) keep the interim rule, before the dashboard (P22).
- **Update (ADR 0034).** P24-3c-2 is done: start-up step 9 loads the open alerts and episodes (`Ingest.load_open`). The advisory switch and the `unpersisted` decision above are unchanged and stay for P24-3c-3 and P22.
- **Update (ADR 0035).** P24-3c-3 is done: `serve.build_app` calls `Wire.enable_advisory` (the advisory is on), and Wire reaches the hub through `LoopHub` (a thread bridge). The `unpersisted` decision above is still OPEN.
