# ADR 0059: REPLAY feeds a stored session through the normal pipeline (S7-3)

Status: Proposed (implements design 3.10 and design 1, Operating mode isolation and Clock abstraction; confirm at the next design review).
Design: Rev 3.45 stays frozen. No wire message, endpoint, setting, migration or constants.json change. The design line: REPLAY feeds the stored frames of a chosen session through the normal pipeline at 1x, 4x or 16x with Pause, into a new session labelled REPLAY in test_db_path, and never writes to the original database; the source is read from db_path through a separate read-only connection.

- **Split of S7-3.** S7-3 (this ADR): everything on the host: the scaled clock, the source, the thread, `--session`, `--speed`, and a `pause()` / `resume()` on the replay object. **Not here: the Pause control a person can press.** The REST endpoint table is frozen at 13 endpoints and a dashboard button needs a new one (and a wire flag for "paused"), which is a design change. Proposed as S7-4. Until then a replay runs to its end at its speed.
- **Start.** `python -m ppe_host.main --mode REPLAY --session N [--speed 1|4|16]`. `--session` is required in REPLAY and refused in any other mode; `--speed` defaults to 1 and is refused outside REPLAY (exit 2 either way, before any file is made). 2, 0 or a word is argparse's exit 2.
- **Checks before a session row is written** (`main.check_replay`, exit 2 with a message): db_path exists, the session is in it, the session has at least one stored frame, and the test database has no open alert and no unresolved episode from an earlier test session. The last one is a refusal on purpose: alerts and episodes stay open across sessions (2.11) and the open-alert index allows one per node and type, so a stale `man_down` from a SIMULATOR rehearsal would hide the one the replay should raise. Resolve it in the dashboard or delete `data/ppe_test.db`.
- **Source.** `services/replay.py`. `connect_readonly` opens db_path with `mode=ro`, so no statement of the replay can write; a test proves a write raises and that the database file is byte for byte the same afterwards. SQLite may leave empty `ppe.db-wal` and `ppe.db-shm` files beside a WAL database it has read. `immutable=1` would avoid them but would ignore the -wal of a host that crashed, so it is not used. The stream is the frames of the session in `event_seq` order and its `base_health` rows as heartbeats, merged by time (a frame first at the same millisecond), read lazily with two cursors. Frames of every stored `verify` value are replayed: the host verifies them again with its own key, so the result is the normal pipeline's.
- **Time offsets.** The offset of an item is its stored `rx_ts` (`ts` for a heartbeat) minus the first, summed from the step between neighbours: a step back counts as no time and one step is cut to `MAX_GAP_S` = 300 s, so a stop of the source (host restart, laptop asleep) does not freeze the replay. Every real silence up to 300 s, which covers the 15 s and 60 s link rules, is kept.
- **ScaledClock.** `clock.ScaledClock(base, speed)` starts at the base values and runs `speed` times as fast (`wall_ms` and `mono_ms`), with `pause()` and `resume()`. Its wall time is the start wall time plus the scaled elapsed time, so the rows of a replay have today's date and the dashboard's "last seen" stays sensible; the stored original times are not reproduced. Every host timer reads it: ingest, rules, health, writer, audio. The OS watchdog and the liveness stamps keep the real clock (`Runtime.real_clock`), because a 3 s stall limit read at 16x would be 0.19 s.
- **ReplayThread.** Delivers each item when the ScaledClock reaches its offset, to `Runtime.gate.on_item` like the SerialReader, so it waits for RECOVERING_EXIT and then goes through verification, the seq classifier, the rules and the writer into `test_db_path`. Its time 0 is the first poll after the gate goes live, so the recovery of the test host does not bunch the first frames. Nothing is dropped or skipped (unlike the simulator, which never catches up): a late poll delivers everything that is due, in order. At the end of the data the clock stops (so no silence alert is made from the end of the data), `finished` is set, and the thread retires its watchdog stamp (`replay`) so a finished replay is not a stalled thread. An error in the reader (a source that cannot be read) is logged, ends the thread the same way, and does not stop the host.
- **Session.** `begin_session` never resumes a REPLAY session: it closes the old one ABANDONED with detail `new_replay`, because a resumed one would hold the frames of the earlier replay. The new session's `session_label` is `REPLAY of session N (MODE, started YYYY-MM-DD HH:MM UTC)`; the snapshot already carries `session_label`, and the TEST banner reads the mode as before. The start-up line ends with `replaying session N at Kx (F frames)`.
- **Runtime.** `Runtime(st, replay=(session_id, speed))`; a replay outside REPLAY mode raises ValueError before anything is built. `Runtime.replay` is the thread (`pause()`, `resume()`, `finished`, `counters`, `error`). It stops before CLEAN_SHUTDOWN and the writer, like the simulator. The serial drain of S7-2 runs in REPLAY too.
- **Observed on the development sandbox, real clock, real Runtime.** A 100 s `link_loss` source at 16x took 6.5 s and gave `sensor_fault` at 26 s, `signal_lost` at 38 s, `link_lost` at 82 s, all cleared at 96 s of source time (the simulator at 1x gave 26, 35, 80 and 96). A 70 s `man_down` source at 4x took 17.8 s and gave `man_down` DANGER at 54 s, as at 1x. The 3 s and 2 s difference is the 1 Hz tick: the host's timer fires once a real second, which at 16x is every 16 s of replay time, so a silence rule can be late by up to `speed` seconds.
- **Decisions to confirm.** (1) The replay refuses to start on a test database with open alerts or episodes. (2) Wall time of the replay is today's date, scaled, not the stored dates; the source's date is in the session label only. (3) `MAX_GAP_S` = 300. (4) A finished replay freezes the clock and the host keeps running on the last state until it is stopped. (5) A new REPLAY never resumes an old one (`new_replay`). (6) The 1 Hz tick stays at 1 Hz real time, so at 4x and 16x the silence rules are up to 4 s and 16 s late. Running the tick at `speed` Hz would fix this but would also send the dashboard 16 updates a second. (7) The Pause control is S7-4. (8) A rehearsal needs an operator in the test database to press Start monitoring (create-operator --db data/ppe_test.db), as for SIMULATOR; a replay does not start monitoring by itself.
- **Checked here (development sandbox, Linux).** `host/tests/test_replay.py`: 45 tests (scaled clock, source, offsets, thread, runtime, begin_session, main, this ADR). Results are in docs/PROGRESS.md.
- **Not here.** A Windows run. A browser run of a replay on the dashboard. A 24 h source. The Pause control (S7-4). The Ctrl+C clean-shutdown fix (open since ADR 0057).
