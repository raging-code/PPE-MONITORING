# ADR 0066: The 130,000-frame write-commit benchmark (`synchronous=FULL` vs WAL)

Status: Decided. This closes the first bullet of CODING_GUIDE.md Section 6 ("Not for chat"): "The 130,000-frame benchmark (decides `synchronous=FULL` or WAL: keep `FULL` if commit p99 with antivirus running is 50 ms or less, otherwise WAL with `synchronous=NORMAL`) ... on the laptop." The audio probe named in the same bullet is a separate, still-open item.

No code, wire, setting, migration or constants change. `host/ppe_host/io/db_writer.py` already defaults every writer connection to `synchronous=FULL` (`connect_db`, `DBWriter.__init__`); this ADR is the record that the default was tested and should stay.

## Tool

`tools/bench_writer.py`, a standalone script (not imported by `ppe_host`, not wired into `cli.py`, CI or the `justfile`). It builds a throwaway copy of the real schema with the repo's own `connect_db` and `run_migrations`, seeds the roster and one session row, then commits 130,000 single-frame rows one at a time (one `BEGIN IMMEDIATE` / `COMMIT` per frame, matching how `DBWriter` commits a routine frame), timing each commit. It runs this twice back to back, same machine and disk: once at `synchronous=FULL`, once at `journal_mode=WAL` with `synchronous=NORMAL`.

## Result (field laptop, antivirus running as in a real shift)

130,000 frames per pass:

| | p50 | p95 | p99 | max |
|---|---|---|---|---|
| `synchronous=FULL` (current default) | 0.93 ms | 8.97 ms | **9.86 ms** | 123.37 ms |
| `journal_mode=WAL`, `synchronous=NORMAL` | 0.06 ms | 0.17 ms | 0.30 ms | 223.95 ms |

A smaller 5,000-frame run on the same machine gave FULL p99 10.42 ms and WAL+NORMAL p99 0.31 ms, consistent with the full run.

## Decision

**Keep `synchronous=FULL`.** Its p99 (9.86 ms) is well inside the 50 ms gate, so the rule in Section 6 does not call for a change. No edit to `db_writer.py`'s default, `connect_db`, or any setting.

## Notes for the record

- WAL + `synchronous=NORMAL` is faster on every percentile up to p99 (roughly 30x at p50), but its **max** (223.95 ms) is higher than FULL's max (123.37 ms) on this run. That is consistent with an occasional WAL checkpoint stall: WAL trades a lower, steadier per-commit cost for a rarer but larger spike when the log is flushed to the main database file. FULL has no such spike because every commit itself is the durable write. This does not change the decision (the gate is on p99, not max), but it is a reason FULL is also the more *predictable* of the two, not only the one that happens to pass.
- Sustained throughput was 527.8 frames/s (FULL) and 1557.6 frames/s (WAL+NORMAL) on this machine. Both are far above anything the system needs in normal operation (3 roster nodes at a sub-1 Hz routine rate), so this benchmark was about per-commit latency under load, not throughput headroom.
- This result is specific to the machine and disk it was measured on. If the field laptop is replaced, or if `host_disk_min_gb`-class storage changes (e.g. a laptop with a spinning HDD instead of an SSD), re-run `tools/bench_writer.py` and update this ADR rather than assuming the old numbers still hold.
- The matching chunked-recovery timing (`RECOVERING_EXIT` within 3 s, ADR 0037) is covered separately by `host/tests/test_p25_release.py`; this ADR's benchmark is only the raw commit-latency half of the Section 6 bullet.
