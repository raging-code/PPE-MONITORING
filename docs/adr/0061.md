# ADR 0061: Pause and resume of a REPLAY host, host side (S7-5a)

Status: Proposed (confirm at the next design review). Decisions A to D below were taken by the author of the part, on the recommendations in the S7-5 proposal.
Design: Rev 3.45 stays frozen; the changes are an addendum at the end of `docs/design/s03-8.md` (REPLAY pause addendum), in the style of the PIN addendum of ADR 0056. This part is the host only. The dashboard button is S7-5b.

- **What.** One new endpoint, `POST /api/replay/pause`, body `{paused: bool}`, answer `{paused, finished}`. It sets the state, it does not toggle. Pausing stops the `ScaledClock` of the replay (ADR 0059), so every timer of the host stops with it: no frame is delivered, no silence rule fires, no alert ages. The OS watchdog and the liveness stamps keep the real clock and are not affected. The endpoint table goes from 13 to 14.
- **Answers.** 200 `{paused, finished}`. 401/403 as for every operator call. 409 `RECOVERING` (with `retry_after_s`) before the replay has started. 409 `STATE_CONFLICT` on a host that is not in mode REPLAY, and on a replay that has finished (its clock stays frozen; a resume cannot restart it). 422 for a body without a boolean `paused` (the body model refuses extra keys, so a speed cannot be sent here). No new error code.
- **Audit.** Migration 0004 adds `REPLAY_PAUSE` and `REPLAY_RESUME` to `audit_actions` (23 rows). The route writes one row when the state changed, with the operator, in the REPLAY session of the test database. A repeat of the state the replay already has changes nothing and writes no row (like `START_MONITORING`).
- **Wire.** `replay: {speed, paused, finished}` is a new field of the snapshot and of the system message, `null` when the host is not in mode REPLAY. It is optional in the generated TypeScript (`replay?: ReplayInfo | null`), so the dashboard and its fixtures compile unchanged until S7-5b. No new message type. A pause or resume sends a system message at once (`Wire.on_replay_changed`); the end of the data (set by the replay thread) is seen by the next 1 Hz tick, because the system message is rebuilt there and `replay` is part of the key that decides whether it has changed.
- **Port.** `Port.replay_set_paused(paused) -> ReplayState(paused, finished, changed)`, implemented by `HostPort` (it does not block, so the route calls it on the event loop like `set_scba_correction`). `serve.build_app` gives the Port the `ReplayThread` of the Runtime (`port.replay`) and the Wire the callable `Runtime.replay_info`.
- **A change in S7-3 code.** `ReplayThread.resume()` does nothing once `finished` is set, and undoes a resume that races with the end of the data; the thread now sets `finished` before it stops the clock (it was the other way round, which left a window in which a resume could restart the clock of a finished replay). ADR 0059 decision 4 (a finished replay freezes the clock) is the rule this keeps.
- **Generator.** `tools/gen_ws_schema.py` accepts the JSON Schema keyword `default` (a field with a default is not in `required`, so it is optional in TypeScript). Nothing else about the generator changed. `test_converter_refuses_a_keyword_it_does_not_know` now uses `examples` as its unknown keyword.
- **Decisions taken.** (A) One state-setting endpoint rather than `/pause` and `/resume`. (B) An audit row for every change (this is what needs migration 0004). (C) Any logged-in operator may pause, as for Acknowledge. (D) No speed control from the dashboard: changing the speed of a running `ScaledClock` means re-basing it, which is a separate part.
- **Changed tests.** Tests that listed the migrations or counted the audit actions now expect 0004 and 23 rows (`test_db_schema`, `test_migration_0003`, `test_cli_backup`); the model round-trip fixtures carry `replay: None`; the endpoint-table test expects 14 endpoints and has the three rows of the new one (200, 409 RECOVERING, 422; 401 and 403 are generated).
- **Checked here (development sandbox, Linux).** `host/tests/test_replay_pause.py`: 27 tests, 3 runs in a row all passed. They cover the route with a fake port (state answers, one row per change, none for a repeat, 409 both ways, 422, 401, 403, no GET), `HostPort.replay_set_paused`, the snapshot and the system message (null off REPLAY, at once on a change, one message for the end of the data), the resume guard of the thread, migration 0004 on a fresh database and on a version 3 database that keeps its rows, and a real REPLAY host built by `build_app` and driven through the real route: 409 while recovering, a pause stops the frames and the clock, a repeat writes no row, a resume goes on to the end, the end shows as `finished` on the next tick, and a pause after the end is 409. Every system message of that test is checked against the models. The rest of the host suite and ruff are in PROGRESS.
- **Not here.** The dashboard button and the Paused banner (S7-5b). A browser run. A Windows run of a replay. A speed control (D). Pausing before the replay has started is refused rather than queued.
