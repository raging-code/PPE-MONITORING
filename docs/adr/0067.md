# ADR 0067: The audio probe (call latency and human-judged audible latency)

Status: Decided. This closes the second half of the CODING_GUIDE.md Section 6 bullet begun by ADR 0066: "The 130,000-frame benchmark ... and the audio probe, both on the laptop." ADR 0066 covers the write-commit half; this is the audio half.

No code, wire, setting, migration or constants change. This does not replace or alter `host/tests/test_audio_wiring.py`'s existing 300 ms test (alert to `backend.play()`, with a fake backend); it measures the part of the chain that test cannot reach: `backend.play()` to an actual human hearing the sound, on the real laptop speaker.

## Tool

`tools/audio_probe.py`, a standalone script (not imported by `ppe_host`, not wired into `cli.py`, CI or the `justfile`). It uses the host's own `WinsoundBackend` and real WAV files (`host/sounds/`), so it exercises the production code path rather than a reimplementation. Two passes:

1. **Call latency** — wall-clock time from `backend.play()` to it returning, for each real alarm sound. Automatic, no human input.
2. **Human-judged audible latency** — the script plays a sound and the operator presses Enter the instant they hear it, repeated 3 times per sound. This is the only way to answer "is it actually audible in time" without extra hardware (a microphone and a separate timing rig), which this script does not assume is available.

## Result (field laptop, real speaker, 3 repeats per sound)

| Sound | Call latency | Audible latency (median) | min | max |
|---|---|---|---|---|
| siren (DANGER / man-down) | 4.7 ms | 256 ms | 120 ms | 2696 ms |
| beep (WARNING) | 0.1 ms | 112 ms | 104 ms | 136 ms |
| one_beep (notice) | 0.2 ms | 128 ms | 128 ms | 128 ms |
| chime (shift chime) | 0.1 ms | 136 ms | 136 ms | 144 ms |
| probe (100 ms silent self-check) | 0.7 ms | not timed (silent by design) | — | — |

**The siren's max (2696 ms, its first of three reps) is a mis-timed button press, not a hardware or software delay**, per the operator's own account at the time of the run. It is kept in the table above rather than dropped, since it was measured and the median (256 ms) already is not pulled meaningfully by it; a reader who wants the cleaner two-rep figure for the siren (120 ms, 256 ms) can use those instead. The other three sounds, each with three closely-clustered reps (spreads of 4 to 32 ms), had no comparable outlier.

## Decision

**No change.** Every sound's audible latency, including the siren's slowest clean rep, lands under the 300 ms design-5 gate with margin (worst clean figure: 256 ms). Call latency is sub-5 ms across the board, confirming the software side of the chain (already covered by the fake-backend test in `test_audio_wiring.py`) is not where any risk would come from; the real-hardware link, measured here for the first time, is not either.

## Notes for the record

- This probe starts its clock at `backend.play()`, not at the sensor frame. It is not the same as the "man-down latch to dashboard ... camera at 120 fps or more" bench timing gate of CODING_GUIDE.md Section 6, which measures the whole sensor-to-speaker chain and needs a camera; that gate remains unmeasured and open.
- The human-timed numbers include the operator's own reaction time (pressing Enter after hearing the sound), so they are an upper bound on true audible latency, not a lower one. The real hardware-plus-perception delay is at most what is shown here, very likely less.
- `--volume-check` was not run / was run and the operator confirmed [FILL IN: muted check, volume level, whether `cli test-alarm` was also run as the reminder suggests].
- As with ADR 0066, this result is specific to this machine, this speaker and this room. Re-run `tools/audio_probe.py` and update this ADR if the laptop, speaker, or operating environment changes materially before a trial.
