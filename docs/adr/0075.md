# ADR 0075: End shift ends every jacket assignment (S8-6a host, S8-6b dashboard)

Status: Proposed (decided with the operator on 2026-11-28; confirm at the next design review).

Design: Rev 3.45 stays frozen. This ADR changes what the existing `POST /api/session/end` (design 3.8) and `close_session('ENDED')` (design 2.3) do inside the same transaction. No new endpoint, no migration, no audit action, no wire message, no setting and no new error code.

## Why

ADR 0071 and 0072 link every stored reading to the person who wore the jacket, through `firefighter_assignments`. Until now an assignment stayed open across End shift, so a new shift began with yesterday's wearers still on their jackets. The dashboard asked who wears what once per browser page (before Start monitoring), and Start monitoring is not pressed again at End shift, so nobody was asked at the start of the second shift. Readings of the new shift were then stored against a person who may have gone home. ADR 0074 listed this as an open point ("End shift still keeps the assignments").

## Decisions

- **A. End shift ends every open assignment, in the same atomic unit.** `close_stmts('ENDED', ...)` (services/sessions.py) gets a fourth statement after the new session is opened: `UPDATE firefighter_assignments SET end_ts = MAX(?, start_ts) WHERE end_ts IS NULL`, with the close time of the session. All rows are written or none: a rolled-back End shift ends no assignment (design 2.3). The order is now: END_SHIFT audit row, close of the old session, new session, end of the assignments. CLEAN_SHUTDOWN and ABANDONED (a host restart) do **not** end assignments: a restart inside a shift resumes the same shift (design 2.3), and the jackets are still worn.
- **B. Nothing is deleted.** The assignment rows stay with their `end_ts`; the people stay active and keep their profile and consent. A reading received before the close stays linked to the person who wore the jacket. A reading received in the same millisecond as the close, or later, belongs to the next shift's wearer (the export's hand-over rule, ADR 0073), so until someone is put on it has an empty firefighter field.
- **C. The END_SHIFT audit row lists what ended.** The reason JSON gets a fourth key, `ended_assignments`: `[[node_id, firefighter_id], ...]`, ids only, never a name or an alias, in node order and empty when nobody wore a jacket. The key is read just before the unit is queued; the UPDATE ends every assignment that is open when the unit commits, so a person put on in that short window is ended too and only the list may miss them.
- **D. The dashboard asks again.** The End shift dialog says that every firefighter is taken off their jacket and lists the jackets that will end (`FF-01: FFR-01`; alias only). After a successful End shift the page reloads GET /api/firefighters (so the node cards show nobody) and shows `New shift jackets`: the same question as before Start monitoring (`WearerConfirm`), with a Not now button. It never blocks anything: alerts, sound and Start monitoring behave as before. It goes away when the operator has confirmed or pressed Not now. A host with no firefighters, or one that does not answer the list, gets no question.
- **E. Why not carry the assignments over.** Carrying them over would be a silent assumption that nobody changed. A forgotten confirmation would then attribute a whole shift's readings, including heart rate and CO exposure, to the wrong person, which is worse for the forecasting work than an empty field. An empty field is visible and honest; a wrong name is not.

## Not here (open points)

- **No confirmation is enforced.** The question can be dismissed with Not now, and the next shift then runs with unlinked readings until someone assigns in Settings. Making it a hard gate would delay monitoring at the moment a fire is going on, so it is not done.
- **Several operators.** Only the screen on which End shift was pressed shows the question. A second screen shows the cards of the new state (nobody on the jackets) at its next poll (30 s, WearerSync) and does not ask; its operator can use Settings.
- **The Word documents** do not describe this yet; it belongs in the consolidated Rev 3.46.

## Tests

`host/tests/test_end_shift_assignments.py` (every open assignment ends at the close time and nothing is deleted; the people stay active; the END_SHIFT row lists the ended jackets by id and never a name; a shift with nobody on a jacket ends nothing; a conflicting End shift ends nothing; the same person can be put on again and the old row keeps the history; a reading before the close stays with the person and one after it is unlinked until someone is put on, through the export), `test_sessions` (the statement order, now four, and the detail with `ended_assignments`). Dashboard: `tests/new_shift_jackets.test.tsx` (the dialog sentence and the jacket list; the reload and the question after End shift; confirming sends /assign and the question goes away; Not now sends nothing; no question without firefighters or when the list is not answered).
