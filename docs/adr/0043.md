# ADR 0043: lock files, version files and lint (P27b-1)

Status: Proposed (decided in the P27b sessions; confirm at the next design review).
Design: Rev 3.45 is frozen (8 and 14.5: lock files and one lint tool per language; 13: `python_lock_sha256` in the build manifest). No host behaviour, frame, migration, constant, setting or REST route changes. P27b is split in three: this part (P27b-1: locks, version files, lint), P27b-2 (`requirements.yaml`, hazards H1 to H22, the CI check for unknown REQ ids) and P27b-3 (REQ ids in test names and the "Spec item has no test" check). The last two are not started.

- **Python locks.** Two files, both with SHA-256 hashes, made by `uv pip compile --python-version 3.12 --generate-hashes`: `requirements.lock` (runtime: what `pyproject.toml` names plus what those need) and `requirements-dev.lock` (runtime plus pytest, Hypothesis, httpx2, pyyaml and ruff, the `dev` extra). The runtime file is the one the build manifest hashes and the release package carries. `tzdata` is pinned (2026.6), because Windows has no time-zone database (design 3.10). Install: `python -m pip install --require-hashes -r requirements-dev.lock`, then `python -m pip install --no-deps -e .` (a hash-checked file cannot hold the project itself). Regenerate with `just lock <cut-off>` (needs uv; a dev tool only).
- **The 14-day cut-off.** `--exclude-newer 2026-11-13` (the lock date minus 14 days): no pin is a release less than two weeks old, the same rule as the pins in ADR 0042. The date is in the header of each lock file and a test reads it.
- **No generated file changed.** With the locked versions (pydantic 2.14.3, fastapi 0.162.5, starlette 1.10.0) all six generators write byte-identical files, so the CI "generated file is stale" check stays green. The lock installs into a fresh Python 3.12 venv with pip and with uv, and `pip check` passes.
- **Version files.** `.python-version` (3.12) and `.nvmrc` (22) say what CI and `requires-python` already said. A test fails if the two files, `pyproject.toml`, the CI workflow or `just lock` disagree.
- **Ruff.** Lint only, rules E9 (syntax errors) and F (unused imports and variables, undefined names, duplicate imports), no formatter, no style rules: they would rewrite code for no safety gain. It found 79 items in `host/` and `tools/`: 68 unused imports, 10 unused variables and one duplicate `import time` (in `clock.py`). The imports were removed. Ten variables in tests hold the result of a call that has to run (a submit, a send, an open); they are renamed with a leading underscore and the call stays. The test result is the same before and after (1319 passed, 3 xfailed; the one failure, `test_both_queries_use_their_indexes`, is an SQLite 3.45.1 difference in the development sandbox and was there before). With the nine new tests in `test_locks_lint.py` the final run on a clean copy with the patch applied is 1328 passed, 3 xfailed and that one failure.
- **Biome.** `@biomejs/biome` 2.6.7 (2.6.8 is 12 days old), exact pin, lint only, no formatter and no import sorting. Preset `none` plus a short list of rules that find real mistakes: unused variables and imports, `debugger`, `==`, duplicate cases and keys, fall-through, assignment in an expression, self-compare, `isNaN`, unreachable code. `src/gen/` is excluded (generated). One finding: `stopTimer` in `worker/runner.ts` is assigned and never read. The watchdog code is not touched; a comment-only `biome-ignore` records why. A temporary file with `debugger` and `==` fails the lint, so it does find things. `just lint` and the CI dashboard job run `npm run lint`.
- **Vitest 4.1.12.** `npm audit` on the dashboard showed 3 findings (2 critical, 1 moderate), all in Vitest 3.2.x (`tinypool`, `@vitest/mocker`). They are in the test runner, not in the dashboard that ships, but the fix is a version bump and not a code change: Vitest 4.1.12 clears them. `npm audit` now reports 0 in `dashboard/` and `e2e/`. The lock changes only Vitest-related packages and Biome. Typecheck, build and all 267 tests (265 pass, 2 expected failures) pass. npm 10 crashes on this upgrade (an Arborist error, "reading 'edgesOut'"), so the lock was written with npm 11; the lock installs with npm 10's `npm ci`, which is what CI runs.
- **Checked here (development sandbox, Linux).** Locks installed with hashes and `pip check`; the six generators unchanged; full pytest on the locked versions (see above); ruff and Biome clean; Biome catches a planted mistake; `npm ci`, typecheck, lint, test and build in `dashboard/`. **Not checked:** nothing has run on a Windows machine or in GitHub Actions; the `just setup` and `just lock` recipes were not run through `just`/PowerShell.
- **Not fixed, please decide.** Biome's recommended accessibility rules flag `AlertCard.tsx` line 27: a click handler on an element that is not interactive, with no key handler. Acknowledge and Resolve are real buttons, so the keyboard test of design 8 is most likely met. Selecting a node card by keyboard may not be. The accessibility rules are not in the rule set above, so the lint stays green; this is a candidate for its own small part.
- **Open, please confirm.** (1) Two lock files instead of one. (2) The 14-day cut-off. (3) No formatter in either language. (4) Vitest 4.1.12 instead of staying on 3.x with open advisories.
