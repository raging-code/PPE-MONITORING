# ADR 0039: purge-session (P26-2)

Status: Proposed (decided in the P26 sessions; confirm at the next design review).
Design: Rev 3.45 is frozen (2.6 step 2, 2.8, 2.11 safety rule, 14.5 CLI, section 8 purge-guard test). Nothing in the migration, `constants.json`, `alert_catalog.json`, the settings keys or `api/models.py` changes: `SESSION_PURGED` was already one of the 18 audit actions.

- **Where the code is.** `services/purge.py` holds the rules (`check_purgeable`, `delete_session`, `compact`, `purge_live`, `purge_copy`, `copies`, `sweep_exports`); `cli.py` has the command `purge-session --session-id <id> [--db] [--home] [--export-dir] [--backup-dir] [--usb-dir ...]` and only does the talking. `main.py` is imported inside the command (it imports `cli`).
- **One transaction, foreign-key order.** `BEGIN IMMEDIATE`, `foreign_keys=ON`, `secure_delete=ON`: ml_outputs (skipped: the Tier 2 table does not exist), alerts, episodes, frames, audit_events, system_events, base_health, advisory_summaries, checkpoints, then the sessions row. The `SESSION_PURGED` audit row (session_id NULL, event_seq 0, operator NULL, reason = the id) is in the same transaction, so the deletion and its record are one fact. `PRAGMA foreign_key_check` runs before the commit: a violation rolls back. After the commit: `wal_checkpoint(TRUNCATE)`, `VACUUM`, `wal_checkpoint(TRUNCATE)`. A test looks for a marker in the file and the -wal file bytes.
- **Refusals, before anything is deleted.** Exit 1, nothing recorded: the host lockfile is live (same test as start-up: PID running and same start time), an open session is monitoring, the session is still open, the id is unknown. Exit 2 with an audit row: an alert of the session with `cleared_ts` NULL, an episode of the session that is not RESOLVED, or a foreign-key violation (for example an alert of a later session that points at a frame of this one; the transaction is rolled back). `audit_actions` is frozen and has no refusal action, so a refusal is a `SESSION_PURGED` row whose reason starts with `refused <id>:`; a reader of the audit log must look at the reason.
- **Copies.** Every `*.db` in `backup_dir` and in each `--usb-dir` is opened, and only a file that holds the session is changed: the read-only attribute is lifted, the same deletion runs (no refusal rules: a copy is a snapshot and the live database already decided), `VACUUM`, and the attribute is put back as it was. A copy without the session, and a file that is not a PPE database, are only read. Copies use a plain connection: `connect_db` would switch a backup to WAL and change a file that does not hold the session. A `--usb-dir` that does not exist (drive not plugged in) is a failure, exit 2, after the live purge has been done; the default `backup_dir` that does not exist is not (no backups yet).
- **Run it again.** A session that is gone from the live database is still swept from copies and exports, so a purge that stopped half way is finished by running the same command. That run writes its own `SESSION_PURGED` row when it removed something; an id found nowhere is exit 1.
- **Exports.** `exports/session_<id>_*.csv` is deleted (`session_10_*` is not matched by id 1). A whole-database export (`export_all_*.csv`, which can hold the session) is not deleted but named in a warning, because it also holds other sessions that must stay.
- **Open, please confirm.** (1) No confirmation prompt and no `--yes`: the command is as 2.8 gives it, and the closed-session and no-open-item rules are the guard; a typed id is final. (2) Downloads the dashboard saved to the operator's own folder are outside the host's reach: `docs/data-governance.md` has to say who removes them. (3) The location of the second drive for the End shift copy is still P26-3; until then `--usb-dir` names it. (4) A refused purge is recorded as `SESSION_PURGED` (see above); a new audit action would be a migration.
