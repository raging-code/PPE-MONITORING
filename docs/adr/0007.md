# ADR 0007: REST actions of P19-2 (session start and end, Acknowledge, Resolve)

Status: Proposed (decided in the P19-2 session; confirm at the next design review).
Design: Rev 3.45 is frozen. Nothing in the frame, the migration or `constants.json` changes.

- **Port grows by six methods:** `recovering_retry_s`, `start_monitoring`, `end_session`, `ack_alert`, `ack_episode`, `resolve_episode`. The host (P24) implements them; the routes check the request, map the answer and write the audit rows the port does not write. A method returns `None` for an unknown id (404) and raises `ApiError` for a conflict.
- **Threads:** Start, Acknowledge and Resolve call the port on the event loop because the engine is single-threaded. End shift is awaited in a worker thread because it runs the backup (design 3.8: off-loop backup), so the port's `end_session` must be thread-safe.
- **Audit ownership:** `END_SHIFT` is written by `close_session('ENDED')` inside its own transaction (2.3), so the route never writes it. `START_MONITORING` is written by the route only when `start_monitoring` reports a change, so a second call adds no row. `ACK_ALERT`, `ACK_EPISODE` and `RESOLVE_EPISODE` are written for every accepted call. A refused call (400, 404, 409, 422) writes no row, because `audit_actions` has no rejection actions apart from `LOGIN_REJECTED` and `ORIGIN_REJECTED`.
- **Check order of End shift:** wrong `confirm_text` 400, then recovering 409 `RECOVERING` (`retry_after_s` = `recovering_target_s`), then a `session_id` that is not the open session 409 `STATE_CONFLICT`. `confirm_text` is a plain string in the model so a wrong value is 400, not a 422 schema failure. The port repeats the session check atomically and may still raise `STATE_CONFLICT`.
- **Acknowledge semantics the real port must keep (P24):** an alert Acknowledge is a 200 also for an alert that already cleared, and a repeat returns the first `acknowledged_ts` and `acknowledged_by`. An episode Acknowledge on an `ACKNOWLEDGED` episode is an idempotent 200 with the stored values; on a `RESOLVED` episode it is 409 `STATE_CONFLICT`, because the answer's `state: 'ACKNOWLEDGED'` would be false (3.8 lists only 404 for this route; proposal). Resolve of a `RESOLVED` episode is 409 `STATE_CONFLICT` (3.8). `latch_still_set` is the node's `mandown_prev` after Resolve.
- **Audit detail (proposal):** `ACK_ALERT` carries `reason = 'alert_id <n>'`, because `audit_events` has no alert column.
- **Not in this Part:** the engine wiring behind the port (P24), the real `authenticate` and login backoff (P19b), `GET /api/sessions` and the remaining endpoints (P19c).
