# ADR 0038: CSV export and the export route (P26-1)

Status: Proposed (decided in the P26 sessions; confirm at the next design review).
Design: Rev 3.45 is frozen (2.5 CSV export and formula protection, 2.11 per-session export, 3.8 `GET /api/export.csv`, 14.5 repo layout). Nothing in the migration, `constants.json`, `alert_catalog.json`, the settings keys, the frame or `api/models.py` changes.

- **Split of P26.** Part 1 (this ADR): `services/csv_export.py` and the route. Part 2: the purge-session CLI (offline, audit row, foreign-key order, sweep of backups and `exports/`). Part 3: the rest of `io/backup.py` (second-drive copy at End shift, read-only backup files, the full `integrity_check` at session end).
- **The view is the export.** `iter_csv` selects from `v_full_log` as it is (all 20 columns, header from the cursor), `ORDER BY event_seq, log_ts`, so the six record types come in strict event_seq order and an alert cleared at 45 comes after the events between. `base_health`, keys, tokens and audit rows whose `session_id` is NULL are not in the view and so not in the file. A session filter is `WHERE session_id = ?` on the view's own column (2.11).
- **Formula protection.** Every text value that starts with `=`, `+`, `-`, `@`, tab or CR gets a leading apostrophe (the list in 2.5 names code, detail and raw_hex; applying it to every text column also covers `level`, `record_type` and `verify` at no cost). `raw_hex` always gets one, even when it starts with a letter, so no hex string is read as a number. Numbers are written as numbers: a negative RSSI is `-68.5`, not `'-68.5`. None is an empty field.
- **Streaming.** A read-only connection, `fetchmany(500)`, one bytes chunk per fetch, UTF-8, `\r\n` line ends, no byte-order mark (a BOM would change the first header name for a program that reads the file). The route hands the generator to `iterate_in_threadpool`, so the event loop never reads a row. A client that goes away closes the generator and with it the connection.
- **Measured (development sandbox).** The 24 h database of P25-4 (about 160,000 rows including 28,800 stored bad frames, 20 MB of CSV): first chunk after 0.26 s, whole file in 1.8 s. `ORDER BY` over the view sorts before the first row, which costs the 0.26 s and some temporary memory; a merge of per-table cursors would avoid it and is not needed at these sizes. `tests/test_csv_export.py` gates the first chunk of 60,000 rows at 3 s.
- **The route.** Token and Origin are checked like every other route (401, 403 before the token). `CSV_EXPORT` is audited before the first byte, with the operator and the reason `all` or the session id, so an export that fails half way is still on record; a failed audit write is a 500 and nothing is sent. `Content-Disposition: attachment; filename="export_<all|session_N>_<UTC>.csv"` and `Cache-Control: no-store`. `session_id` must be an integer of 0 or more (else 422 VALIDATION_ERROR).
- **Open, please confirm.** (1) A `session_id` that does not exist gives the header row only, because the frozen list in 3.8 gives this endpoint no 404; a 404 NOT_FOUND would help the operator and needs a design line. (2) No file is written to `exports/`: the design's purge deletes `exports/session_<id>_*.csv`, which suggests operators keep copies there, but nothing in 2.5 or 3.8 makes the host write one (the dashboard saves the download itself). (3) Excel shows the apostrophe of a text literal as a character when it opens a CSV; this is the price of the rule in 2.5, and a leading-apostrophe-free alternative (`="..."`) would be a formula itself.
