# ADR 0037: Restart recovery, RECOVERING_EXIT and the session close (P25)

Status: Proposed (decided in the P25 sessions; confirm at the next design review).
Design: Rev 3.45 is frozen (section 1 restart sequence, 2.3 session resume and `close_session(kind)`, 2.11, 14.5 start-up steps 11 to 13, 14.6). Nothing in the frame, the migration, `constants.json`, `alert_catalog.json`, the settings keys or `api/models.py` changes: every row kind used here (`END_SHIFT`, `CLEAN_SHUTDOWN`, `SESSION_ABANDONED`, `BACKUP_OK`, `BACKUP_FAIL`, `RECOVERING_EXIT`, `HOST_GAP`, `INTEGRITY_OK`) was already in migration 0001.

- **Split of P25.** Part 1 `services/recovery.py` (the rebuild of the engine state from the last 30 minutes of frames). Part 2 `services/recovery_run.py` and the wiring (steps 11 to 13 as a task after the 1 Hz driver, `Runtime.recover`, `Wire.unconfirmed`). Part 3 `services/sessions.py` (`close_session(kind)`), End shift (`HostPort.end_session` and its backup) and the clean-shutdown close. The timing check on a 24 h database and the soak are measurements, not code.
- **One `close_session`.** `services/sessions.close_stmts(kind, ...)` builds the rows once, in the order of 2.3: the `END_SHIFT` audit row (ENDED) or the `CLEAN_SHUTDOWN` or `SESSION_ABANDONED` system row in the old session, then `ended_ts` and `end_kind` in one UPDATE, then, for ENDED only, the new session. `begin_session` runs the ABANDONED close on its own connection inside the start-up transaction (`run_stmts`); ENDED and CLEAN_SHUTDOWN run as one unit of the DBWriter. The rows `begin_session` wrote before are unchanged (ADR 0029 said P25 might move that code; it did).
- **Atomic units.** A DBWriter unit used to fall back to row-by-row commits on a deterministic failure (Rev 3.36). That is wrong for a session close: it could leave the old session ended and no new one, and every later row would fail its foreign key. `Unit.atomic` makes a deterministic failure roll the whole unit back, mark it `failed`, count it (`write_rejected`, LOGGING_FAULT) and move the queue on. A transient fault is still retried in place.
- **The new session id is chosen by the caller** (`max(session_id) + 1`, under `HostPort._end_lock`), because the Ingest must write into the new session from the moment the unit is queued. Units queued earlier belong to the old session and commit first. If the unit fails, `Ingest.undo_end` puts the old session back; rows queued in that short window carried the new id and are rejected by the writer (counted, LOGGING_FAULT). A failed End shift is a 500 INTERNAL_ERROR and the shift stays open.
- **What carries over.** The new session copies mode, host build and both hashes from the old row and carries `monitoring_active` (2.3). It does not carry the operator or the label: `start_monitoring` sets them only while they are NULL and is idempotent per session, so the label of the new shift is the operator's to set. Open alerts and episodes are not touched (2.11).
- **The END_SHIFT reason** is compact JSON: `open_alerts` `[node_id, type]`, `open_episodes` `[episode_id, node_id, state]` over every session, and `latched_nodes` (the jacket latch still set, from the engine). It is the open list that D8 asks End shift to log.
- **The backup** runs after the commit, in the worker thread that serves the request (never on the event loop): `io/backup.online_backup` to `<backup_dir>/end-shift-<UTC>.db`, then `verify_backup`. `BACKUP_OK` (detail: the file name) or `BACKUP_FAIL` (detail: the reason) is a system row of the new session. A failed backup does not undo the close: `backup_ok` is false and the shift is over. The second drive and the purge are P26.
- **Clean shutdown.** `Runtime.stop(clean=True)` queues `close_session('CLEAN_SHUTDOWN')` after the serial reader has stopped and drains it with the writer. `main()` passes `clean=True` only when the server returned by itself (SIGINT or SIGTERM). A start that failed at step 10, a crash or an OS-watchdog exit leaves the session open, so the next start resumes it under the 30-minute rule. Consequence to confirm: after a clean shutdown the next start opens a new session with `monitoring_active = 0`, so the operator presses Start monitoring again.
- **Open, please confirm.** (1) A second tab learns of the new session only on reload: there is no WebSocket message for a session change (the contract is frozen), and its End shift with the old id gets STATE_CONFLICT, as designed. (2) The wire still has no link state "unconfirmed (host gap)"; a node without a fresh frame shows `not_connected` (P25-2). (3) The full `integrity_check` at session end (2.5) is covered by `verify_backup`, which runs it on the backup copy; the live database is checked after RECOVERING_EXIT only.
