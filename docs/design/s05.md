## 5. Timing and link budgets

All are Spec from the summary's gate table and D8 text. All stay provisional until their D-test passes, and no result is called passing until the criteria are confirmed with the adviser and safety reviewer.

| Path | Budget | Status | How it is checked |
|---|---|---|---|
| Man-down: jacket latch to dashboard | 95% within 5 s and 99% within 10 s over at least 100 events in the room gate configuration. A corridor run of at least 30 events is reported without a threshold. Report observed shares with exact 95% intervals, because 100 events only bound the miss rate at about 3%. | Spec, provisional | Camera at 120 fps or more filming the buzzer-driver or amber-LED line and the dashboard together (node and laptop clocks are not synchronised) |
| Base offline detection | 5 s or less | Spec | D8 |
| Dashboard stale detection | 4 s or less | Spec | D8, using server timestamps |
| Dashboard feed stalled to NO LIVE DATA | No tick for 4 s shows the full-screen red state with a repeating tone. This is the feed timeout for the Web Worker. | Spec | D8, with the tab hidden and with only the main data socket blocked |
| Host task stalled | Serial-reader, processing or tick task stalled over 3 s restarts the process and shows RECOVERING. Process back within 5 s. | Spec | D8 |
| Base panel with the host killed | Alarms and identifies the node within 2 s of a valid frame, host killed and USB unplugged. With no host tick for 5 s the panel shows LAPTOP OFFLINE. | Spec | D8 |
| Link-loss state, panel against dashboard | Same state on both at 15 s and at 60 s, after an adverse and after a non-adverse last frame | Spec | D8 |
| Routine silence | Silences over 12 s counted per node and reported as a rate per node-hour with an exact two-sided 95% interval. | Mean routine loss | Reported against the 15% planning ceiling. Not a pass/fail gate. | Spec | Same run |
| Dashboard share of the man-down path | Message received to pop-up visible: 500 ms or less (visual path only; the alarm sound is the host share below), median and maximum reported over at least 100 events. It is part of the 5 s and 10 s man-down budget, not extra. | Proposed, provisional | Browser performance marks (receive, render) in the Playwright run; the camera method still checks the whole path |
| Host share of the man-down path | Frame received from the serial line to broadcast: 200 ms or less; broadcast to host alarm sound start: 300 ms or less (Rev 3.27, provisional); median and maximum over at least 100 events | Proposed, provisional | backend_ms and srv_ts logged per frame; alarm start time measured in the test build with a mocked audio sink, plus one camera or microphone check |
| RECOVERING duration | Open alerts shown at once; replay finished in 3 s or less for a 24 h session | Proposed, provisional | Soak test (2.9) with a 24 h database |

The man-down row is the gate. The older "node event to dashboard display: typical 3 s" stays only as a Proposed target for routine updates, reported and not gated. The "feed stalled to local alarm" timeout is 4 s. Arithmetic check of the man-down budget (Rev 3.28, Proposed; sums of Summary and design values, not measurements): latch within one 10 Hz loop 0.1 s; wait for the node's next free 500 ms send slot up to 0.5 s; event stagger up to 0.17 s (node 3); LBT deferral and backoff up to 0.14 s; frame airtime 0.07 s at SF7; serial line 0.04 s (512 B at 115200 baud); host share 0.2 s; then the host alarm (0.3 s) and the browser visual (0.5 s) run in parallel from the broadcast, so the later one, 0.5 s, counts. The first attempt therefore reaches the dashboard in about 1.7 s. Each lost send adds about 1.9 s (RESEND_WAIT 1.65 s plus LBT, airtime and serial), giving about 3.6 s after one loss, 5.5 s after two and 7.4 s after three, which is the last allowed retry. So the 5 s gate tolerates one lost send, the 10 s gate up to three, and the 300 ms host alarm term does not change either gate. D9 measures real losses, which are not independent.
