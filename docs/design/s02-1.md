## 2. Database

### 2.1 Engine and rules

| Item | Decision | Status |
|---|---|---|
| Engine | SQLite, file ppe.db, WAL mode | Spec (frozen Rev 2.7) |
| Writer | One writer thread, nothing else writes. Items reach it through a bounded queue. | Spec (one writer), Proposed (bounded queue) |
| Readers | Commits and CSV export run off the event loop so they cannot trigger the 3 s stall restart. API reads use separate read-only connections. Every REST read, not only the CSV export, runs in a thread pool on its own read-only connection, so a large query such as GET /api/sessions cannot stall the event loop (Rev 3.25). | Spec (off the event loop), Proposed (read-only connections) |
| Overflow | A full queue is counted and logged as an error. Rows are never dropped silently. All frames share the one ordered writer queue (2.10). Diagnostic frames (bad length, CRC or MAC) are rate-limited: the first 20 per minute are stored and the rest only counted, so a flood of noise cannot starve real frames. A queue overflow or write error shows LOGGING FAULT on the dashboard. | Proposed |
| Schema | Versioned, ordered migrations, frozen with the ABI | Spec |
| Pragmas | Enforced inside a single Python sqlite3 connection factory (connect_db(path, readonly=False)) on EVERY opened connection (since SQLite PRAGMAs are per-connection): PRAGMA foreign_keys=ON; PRAGMA busy_timeout=5000; and on the writer connection PRAGMA journal_mode=WAL; PRAGMA synchronous=FULL; (default; the per-commit cost is UNMEASURED until the 2.10 benchmark runs, and 2.10 gives the rule for switching to NORMAL). | Proposed (FULL is the default; the NORMAL switch rule is in 2.10) |
| Timestamps | Integer UTC milliseconds (_ts), plus a monotonic millisecond counter (_mono) where ordering matters | Proposed |
| Identity | Responders stored as node ID and alias code (FF-01), never names | Spec |
| Unknown node IDs | Rejected and counted, not stored in frames. Counts go to system_events (kind COUNTERS). | Spec (rejected, counted), Proposed (where counted) |
| Secrets | The CMAC key never enters the database, logs or CSV. Login tokens are stored as hashes only. | Spec (keys), Proposed (hashing) |
| Event order | event_seq: one database-wide, monotonically increasing counter shared by every stored event row: frames, alerts (both the raised event_seq and cleared_event_seq), audit_events, system_events and advisory_summaries (six columns in five tables; checkpoints.last_event_seq only records a watermark). It never resets, not at End shift and not in a new session: the new session continues the same counter, and close_session(kind) clones no rows, so it needs no event_seq values except for its own audit and system_events rows. The UNIQUE(session_id, event_seq) indexes therefore only guard against duplicates inside a session. On host start/restart event_seq initializes to (the maximum over all six columns of COALESCE(MAX(column), 0)) + 1, taken over the whole database, not only the open session. Orders events inside a session and in v_full_log. Gaps are expected (Rev 3.28): an event_seq taken by a unit that the full writer queue later drops (routine or diagnostic frames only), or by a unit not yet committed at a crash, is never reused. Only 'unique and increasing' is guaranteed; no export, test or rule may assume contiguous numbers, and HOST_GAP is computed from timestamps, not from event_seq. rx_ts is for display and CSV timestamps only. | Proposed |
