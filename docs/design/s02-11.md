### 2.11 Database changes since Rev 3.26

- Sessions are reporting windows and do not own live state. close_session(kind) closes one sessions row and opens the next in one transaction (the idx_sessions_one_open rule stays). It no longer clones open alerts or episodes. Removed: carried_from_alert_id, carried_to_*, the CARRIED_OVER state and alert_id_map. Migration 0001 in Section 11 was rewritten in Rev 3.27 and run in SQLite: a second open man_down for a node is rejected in the same and in a later session; an unknown alert type and a CARRIED_OVER episode state are rejected; v_full_log selects; foreign_key_check is empty. Section 2.3 prose, the session-end API, close_session(kind) and the session tests were updated to match.

- close_session(kind) never changes alerts or episodes. ABANDONED and CLEAN_SHUTDOWN only close the sessions row. After any restart, recovery finds open alerts by cleared_ts IS NULL and open episodes by state IN ('OPEN','ACKNOWLEDGED') in every session. Episode states are OPEN, ACKNOWLEDGED and RESOLVED only, so a stale open episode is closed only by Resolve. Statement order in the ENDED transaction: write the END_SHIFT audit row in the old session, set the old ended_ts and end_kind, then insert the new sessions row (idx_sessions_one_open rejects the reverse order, which the Rev 3.25 text listed).

- The open-alert unique index becomes global: UNIQUE(node_id, type) WHERE cleared_ts IS NULL. The same applies to open episodes. Open items are found by cleared_ts IS NULL, not by session_id. alerts.session_id means the session in which the row was opened; a per-session export selects rows by the session_id column of v_full_log, so the cleared row of an alert that outlives its session stays with the session that raised it (Rev 3.40); an export without session_id covers every session, so an alert and its clear are never separated.

- Safety rule for per-session purge: purge-session refuses (exit code 2, audit row) if any alert or episode opened in that session has cleared_ts IS NULL. This stops a purge from deleting live state that now outlives its session. The purge runs in one transaction with foreign_keys=ON and rolls back (exit code 2) on any foreign-key violation, so rows in a later session that reference the purged session also block it.

- CHECK lists for alert types, system event types and audit actions are replaced by lookup tables (alert_types, system_event_types, audit_actions) with foreign keys, seeded from alert_catalog.json. The 25 alert types go to alert_types; the 7 banners are not alert types. audit_actions has 18 rows. A catalog change is a data migration (INSERT), not a table rebuild. A startup test fails if the lookup tables and alert_catalog.json differ. CHECK stays only for stable sets (levels, verify, booleans). Migration 0001 seeds audit_actions with 18 rows, alert_types with 25 and system_event_types with 29 (the 26 earlier kinds plus AUDIO_FAULT and AUDIO_OK, and CLEAN_SHUTDOWN added in Rev 3.40 because close_session('CLEAN_SHUTDOWN') writes that row). idx_alerts_one_open_per_node_type still lists the single-open types in its WHERE clause, so changing that list means dropping and recreating that one index, not rebuilding the table.

- Advisory rows: written on change of the advisory risk, plus one heartbeat row per node every advisory_heartbeat_s = 300 (host setting, Proposed). Each written row still takes an event_seq. Any staleness test on advisory data uses a threshold above 300 s. Section 3.5 and the CSV follow this.
