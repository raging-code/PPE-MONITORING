## 1. Host processing, recovery and configuration

Per-frame order (Spec + Rev 3.2/3.17 Fix). Validate 23-byte length, CRC-8, AES-128-CMAC (using sys_id and shared 16-byte key via Python cryptography.hazmat.primitives.cmac.CMAC) and roster (note: LoRa sync word is stripped by the SX1276 radio PHY before serial framing and is not present in raw_hex); deduplicate byte-identical (node_id, boot_ctr, seq) copies within dedup_window_s = 5 s (including boot_ctr prevents a fast <5 s node reboot from colliding with a pre-reboot seq=0 frame); classify sequence (fresh, duplicate, reboot, suspect; the rule is in the Sequence classifier below); evaluate deterministic rules (Section 14; raise-only for suspect frames, 14.1) using an injected monotonic/wall Clock abstraction so LIVE, 4x/16x REPLAY, SIMULATOR, and unit tests share identical timer semantics; allocate the next value of the database-wide monotonic event_seq on the host event loop at event creation/enqueue time (never inside the UI or the SQLite writer thread, preserving exact causal order in the single ordered writer queue); commit frame/alert/episode rows through that queue BEFORE WebSocket broadcast, subject to commit_wait_ms = 120 ms (below the 200 ms host budget). Final level is max(node_level, backend_level). The shadow estimator is a cross-check only. Tier 2 steps (HR, COHb, forecast, anomaly) are skipped in Tier 1.

- Serial layer & frozen Base-to-Host JSON ABI (Proposed — Frozen for Build). A dedicated reader thread (pyserial-asyncio is avoided on Windows) reads 115200 baud (8N1, LF-terminated) using bounded reads ser.readline(513) (max_line_bytes + 1) and decodes with errors='replace' so 74880-baud ESP32 ROM boot garbage lacking \n cannot block or overflow memory. Any line >=512 bytes is discarded until the next \n and increments serial_framing_errors (reported in COUNTERS). DTR and RTS are explicitly set False before opening the port. The Base forwards all sync-matched frames—including frames failing length, CRC, or MAC (rate-limited on the Base to <=20 bad frames/min)—with base_verify set to OK | BAD_LEN | BAD_CRC | BAD_MAC so the host can log diagnostic frames and detect MAC_DISAGREE. Partial lines, bad JSON and binary garbage are counted and dropped; port loss/return logs SERIAL_LOST / SERIAL_BACK. Fuzz-test the parser. While the port is lost, the reader thread retries opening it every serial_retry_s (1 s) with DTR and RTS False and never blocks the event loop; no frames arrive meanwhile, so the base_offline_s rule raises BASE OFFLINE, and SERIAL_BACK is logged when the port reopens. Host-to-Base host_tick (Rev 3.21, Proposed): the event loop's 1 Hz tick timer builds the tick and puts it in a one-slot queue (a newer tick replaces an unsent one). A dedicated SerialWriterThread writes it to the port with write_timeout = serial_write_timeout_ms (200 ms, host-only setting, provisional); the event loop never writes to the port. A write that times out or fails logs SERIAL_LOST once for that outage (detail "write", no second row if the reader already logged the outage), drops that tick without retrying it (the next tick carries the current state) and never blocks the event loop; the first successful write after it logs SERIAL_BACK. The writer thread is not in the watchdog liveness set: a stuck write shows on the base as no host tick for 5 s (LAPTOP OFFLINE) and does not restart the host.

- Slow clients (Proposed + Rev 3.17 Per-Connection Sequence Fix): each dashboard connection has its own bounded send queue (max 64 messages), sender task (1 s send timeout), and per-connection monotonic srv_seq counter starting at 0 on snapshot. Coalescing reading updates inside one client's queue never creates gaps in that client's srv_seq stream, eliminating false snapshot reload loops. A client exceeding the 1 s send timeout is closed with code 4408 and logged as CLIENT_DROPPED.
