Restart & deterministic recovery sequence (Spec + Rev 3.6/3.17 Non-Blocking Replay Rules). The host enters RECOVERING, resumes the open session ONLY if session.mode == startup_mode, the constants and settings hashes match and the last committed row is <30 min old (otherwise close_session('ABANDONED') runs first and a new session opens). To prevent task_stall_s (3 s) crash-loops on large 24 h databases (~129,600 frames), recovery NEVER runs a synchronous row-1 loop on the asyncio thread: (a) incoming live serial frames arriving during RECOVERING are buffered in a bounded pre-replay queue (up to pre_replay_queue_max = 500 frames; if it ever fills, the oldest frames with node level NORMAL and no event bits are dropped first, a frame with mandown, mayday or DANGER set is never dropped, and drops are counted in COUNTERS as pre_replay_dropped) and processed immediately after replay exits so no live emergency frame is dropped; (b) open alerts and open episodes are loaded directly via indexed SQL queries, and active node state is rebuilt (checkpoints are dormant in Tier 1, 2.10; a changed constants or settings hash never reaches this step because it closes the session first, 2.3) via chunked async queries of 2,000 rows per yield—touching task liveness heartbeats on each yield—over open alerts/episodes plus the trailing 30-minute frame window rather than scanning 130k historical frames from row 1 (Rev 3.42: the window ends at anchor_ts, the rx_ts of the newest stored frame row of any session, and starts 30 minutes before it, not before the restart, so an outage of up to session_resume_max_min = 30 minutes never leaves it empty; the frames are read with rx_ts BETWEEN anchor_ts - 1800000 AND anchor_ts and no session_id filter)); (c) the 30-minute CO trend chart per node is rebuilt directly from SELECT rx_ts, co_x10 FROM frames WHERE verify = 'OK' AND seq_class != 'duplicate' AND rx_ts >= :now_ms - 1800000 ORDER BY rx_ts ASC with no session_id filter (:now_ms is the wall clock at restart, not anchor_ts, because the chart is a rolling wall-clock window and a short outage leaves its right side empty, Rev 3.42), so a restart soon after End shift or an ABANDONED close still sees the previous session's frames (Rev 3.28) (at most ~2,700 indexed rows across 3 nodes, <15 ms; the 30-minute window edge uses wall-clock rx_ts, an accepted Tier 1 risk: a laptop clock step of s seconds moves the window edge by s seconds, and the chart is display-only, so no rule or alert reads it); (d) monotonic timestamps from prior epochs are re-based using the per-epoch mono_offset_ms recorded in HOST_START so a Windows reboot inside the 30-minute resume window never corrupts timers; and (e) rejected_frames diagnostic totals are restored from the latest COUNTERS row in system_events plus any subsequent frames WHERE verify != 'OK' (avoiding undercount from the 20/min diagnostic storage cap). Banner vs. Alerts Ownership: node/field safety and notice events live in alerts; host/system banners (recovering, base_offline, no_live_data, host_gap, logging_fault, host_power, audio_fault) live in system_events and live host state only (never inserted into alerts). Mid-Replay Lock & Banner Order: while recovering=true, POST /api/session/end returns HTTP 409 and host_tick sends recovering=1 (Base OLED displays HOST RECOVERING). Sequence on host restart: (1) host down >4 s -> full-screen NO LIVE DATA (siren); (2) reconnect -> snapshot with recovering=true clears NO LIVE DATA and shows RECOVERING banner (one beep) + open alerts; (3) replay ends -> RECOVERING clears, recovering=0, and HOST_GAP banner (one beep, kept until POST /api/system-banners/host_gap/ack) shows exact downtime from last committed row to RECOVERING_EXIT, while each node displays grey 'unconfirmed (host gap)' until its first fresh frame. [Rev 3.27: no checkpoint is written in Tier 1, so recovery always takes the missing-checkpoint rebuild path (open alerts and episodes plus the last 30 minutes of frames; SCBA corrections from audit_events)] Rebuild rule (Rev 3.40): the rebuild feeds the stored frames of the window through the same step() as live frames (14.6) in a rebuild mode that applies the resulting state only and discards every effect: it inserts no alert, episode, audit or advisory row, broadcasts nothing, plays no sound and raises no one-shot notice. Open alert and episode references in the state are bound to the rows loaded in step (b), so a rule that would raise something already open changes nothing. A node whose latest episode is RESOLVED while its last frames still show mandown=1 is restored as latched after Resolve (the LATCH STILL SET ON JACKET row), so the first live frame after a restart does not open a new episode for an incident that was already resolved. When the window holds no frame for a node, that node has no baseline and the first-seen rules of the Sequence classifier above and of 14.1 apply. Accepted over-alarm (Rev 3.42, Proposed, confirm with the adviser): a node whose newest episode was RESOLVED and that sends no frame for more than 30 minutes opens a new episode if its first frame afterwards shows mandown=1, because that frame cannot be told from a new fall outside radio range; the operator Resolves it again. A rule that hid it could hide a real emergency, so none is added.

Time handling & monotonic epoch rebasing (Proposed + Rev 3.17 Fix). event_seq (one database-wide monotonic integer allocated on the host event loop; it never resets, see 2.1) is the sole ordering authority for events and v_full_log, so a laptop NTP clock step cannot reorder history; rx_ts (UTC ms) is recorded for display, elapsed-time rendering, and CSV timestamps, while node uptime_s is never treated as wall-clock time and backend_ms measures host processing duration only. Because Windows GetTickCount64 / time.monotonic() resets to 0 on a laptop reboot (such as battery exhaustion within the 30-min resume window), every HOST_START system_events row records host_boot_id and mono_base_ms, and replay rebases stored rx_mono values relative to the active boot epoch. Each host start generates a new UUID epoch ID and per-connection srv_seq starts at 0.
