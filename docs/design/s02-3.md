### 2.3 Columns

schema_version: version INTEGER PK (migration number); applied_ts (UTC ms); description. The host refuses to start if the database version is newer than the code. Before any migration it takes an online backup (2.6), not a plain file copy, because the WAL is active.

operators: operator_id PK; display_name UNIQUE (shown in the audit log); token_hash (hex HMAC-SHA256 of a secrets.token_urlsafe(24) login token, keyed with server_salt from config/secrets.json, see section 4; never the raw token and never a plain SHA-256); active (0 or 1); created_ts. Role is not used in Tier 1 (decided). Proposed: token_issued_ts only. Tier 1 tokens do not expire (4.1), so there is no token_expires_ts column.

roster: node_id PK (CHECK 1 to 3 in Tier 1); alias UNIQUE (for example FF-01); active. Tier 1 limit: a larger Tier 2 roster needs a new migration that rebuilds roster, because SQLite cannot alter a CHECK in place. Rev 3.36: Migration 0001 also has trigger trg_frames_roster on frames, which reads roster. A rebuild that drops roster fails with the error no such table: main.roster while that trigger exists, so the Tier 2 migration sets PRAGMA foreign_keys=OFF before BEGIN and then, in one transaction and in this order: DROP TRIGGER trg_frames_roster; create the new roster table; copy the rows; drop the old roster; rename the new table to roster; CREATE TRIGGER trg_frames_roster again with the same text; COMMIT; PRAGMA foreign_keys=ON; PRAGMA foreign_key_check (must return no rows). Any future rebuild of frames must also recreate the trigger, because dropping a table drops its triggers.

Session resume & unified close_session(kind) lifecycle (Spec + Rev 3.17, amended Rev 3.27). A host restart inside a shift resumes the open session (ended_ts NULL) ONLY if session.mode == startup_mode AND the last stored row across frames/alerts/audit_events/system_events is <30 minutes old (session_resume_max_min = 30); otherwise the stale open session is closed first via close_session('ABANDONED') (logging SESSION_ABANDONED with detail stale_30min, or mode_changed when the startup mode differs) and a fresh session opens. If constants_hash or settings_hash (computed over canonical sorted-key UTF-8 JSON) differ from the open session's, the host does not resume it (Rev 3.40, as in the Technical Summary section 8): it closes it with close_session('ABANDONED') (logging SESSION_ABANDONED with detail config_hash_changed), opens a new session that records the new hashes and logs CONFIG_CHANGED in the new session, so a session's hashes always describe the thresholds and settings that produced its rows. Open alerts and episodes are unaffected (2.11) and recovery rebuilds node state from them plus the last 30 minutes of frames (checkpoints are dormant in Tier 1, 2.10). Sessions are reporting windows and do not own live state (2.11). Unified close_session(kind) invariant: EVERY session closure (end_kind = 'ENDED' for End shift, 'CLEAN_SHUTDOWN' or 'ABANDONED') runs one atomic BEGIN IMMEDIATE transaction in this order: (a) write the END_SHIFT audit row (ENDED), or the CLEAN_SHUTDOWN or SESSION_ABANDONED system_events row, into the old session; (b) set the old session's ended_ts = :close_ts and end_kind = :kind (this must come before any new sessions row, because idx_sessions_one_open allows only one row with ended_ts NULL); (c) for 'ENDED' only, insert the new sessions row (:new_sid) carrying forward monitoring_active; (d) commit. It never changes, clones or closes alerts or episodes: they keep their ids and stay open across the session change, so the dashboard keeps its cards and does not re-chime, and recovery finds them by cleared_ts IS NULL (alerts) and state IN ('OPEN','ACKNOWLEDGED') (episodes) in any session.

frames. One row per received frame. Frames that fail length, CRC or MAC are stored with verify set, as diagnostics and not readings. Decoded columns are NULL when the length is wrong, and raw_hex is always kept. Duplicates (byte-identical node_id, boot_ctr, and seq within 5 s) are stored and flagged, because every frame is logged. Frames from node IDs not in the roster are rejected and counted, not stored. Order of checks: CRC and MAC come first. Because frames.node_id has no SQLite foreign key constraint, a frame failing length, CRC, or MAC is stored as a diagnostic regardless of what node_id byte it claims (and never updates live node state), while the roster check applies only after verify = 'OK' passes. Reserved values (flags level 3, a set reserved bit in status4) are stored, marked seq_class suspect and logged. Rev 3.35: the database enforces this too: trigger trg_frames_roster (Migration 0001) aborts the insert of any frame with verify = 'OK' whose node_id is not in roster, so a host bug cannot store one. The trigger checks that the roster row exists, not roster.active, and leaves frames that fail length, CRC or MAC alone. Tests and the SIMULATOR must run seed-roster (or insert the roster rows) before they insert OK frames.

Indexes: (node_id, rx_ts), (session_id, rx_ts), and (session_id, event_seq). Rev 3.20 constraints: the boolean columns (operators.active, roster.active, sessions.monitoring_active, frames.co_over_range, alerts.authenticated, and in Tier 2 ml_outputs.early_warning and anomaly_unusual) carry CHECK (x IN (0,1)), and a frames row with verify = 'OK' must have a node_id. The view v_readings filters verify = 'OK' AND seq_class != 'duplicate' (excluding duplicate retransmissions so Tier 2 windows never double-count samples). suspect frames are shown grey in the UI and cannot clear a level. Rev 3.38: episodes.resolved_ts and sessions.end_kind are paired with state and ended_ts by CHECK. There is deliberately no CHECK that cleared_ts is not before raised_ts and none on the hum range: ordering inside a session uses event_seq, not wall-clock ts, and a clock step or an unexpected value in an authenticated frame must never make a write fail (a rejected write is not retried forever, see the write_rejected rule).

Alert types & system banners (Spec + Rev 3.17 Strict Separation). Every row in alerts has its type validated by a foreign key to the alert_types lookup table, which Migration 0001 seeds from alert_catalog.json (Rev 3.27) (25 responder/field alert types; the 7 host/system banner types—no_live_data, base_offline, logging_fault, host_gap, recovering, host_power, audio_fault (3.12)—live in system_events and live host banner state ONLY and are not in the alert_types lookup table (Rev 3.27) so system banners can never create rows in alerts). Open-alert uniqueness (Rev 3.20): the partial unique index idx_alerts_one_open_per_node_type allows at most one open row (cleared_ts IS NULL) per node and type across ALL sessions (Rev 3.27) for mayday, man_down, co_threshold, link_lost, signal_lost, checkin, scba_expired, sensor_fault, battery_low, heat, shadow_notice, node_danger, wrist_open, button_stuck, missed_event and co_warmup. The rule engine updates or clears that row and never inserts a second one. If an insert hits the index it is a rule-engine defect: the insert is refused, the existing open row stays authoritative, and the host logs LOGGING_FAULT with the node and type in detail. unauth_alert is left out of the index and is coalesced by the rule in 14.1b. close_session(kind) clones nothing: an open alert stays open across the session change. The partial index idx_alerts_open (node_id, type) WHERE cleared_ts IS NULL serves the open-alert lookups used by recovery and End shift, and idx_alerts_session_cleared (session_id, cleared_ts) serves per-session reports.

episodes (Spec + Rev 3.5/3.17, amended Rev 3.27). episode_id PK; session_id FK (the session in which the episode opened); node_id FK; kind (Tier 1 allows ONLY 'MAN_DOWN' and 'MAYDAY', matching the node's hardware latch); opened_ts; state ('OPEN', 'ACKNOWLEDGED', 'RESOLVED'); acknowledged_ts; acknowledged_by FK; resolved_ts (Rev 3.38 CHECK: non-NULL exactly when state = 'RESOLVED'); resolve_reason ('rescued', 'false_alarm', 'device_removed'; CHECK: required when state = 'RESOLVED', and NULL otherwise); resolved_by FK. Idempotency invariant: at most ONE episode per node_id may exist in state IN ('OPEN', 'ACKNOWLEDGED') globally (partial unique index idx_episodes_one_active). An open episode outlives its session: close_session(kind) never changes episodes and only Resolve closes one. Upgrading an active MAN_DOWN episode to MAYDAY records an EPISODE_ESCALATED row in audit_events (preserving full transition history) and updates kind in place to MAYDAY.

- Resolving in the database does not clear the jacket latch. Only the jacket CANCEL clears it (errata 3).

- An episode opens on the node's latch (Spec: mandown 0 to 1). Proposed: also when the first frame seen already has mandown=1 (host started while the node is latched, or a new session after a restore). A MAN_DOWN latch upgraded to MAYDAY (status4 bit 4 set while mandown stays 1) changes the open episode's kind to MAYDAY and does not open a second one.

- Resolve resets the backend shadow timing. The backend never opens an episode itself (Proposed): a new episode opens only when the node reports mandown=1 (new latch), because a resolved row is never reopened. If the backend shadow sees 30 s of stillness while the node is not latched, it raises a shadow_notice ("shadow: still 30 s, node not latched"), with no episode, siren or level. The Technical Summary's wording "fresh 30 s stillness may open a new episode" in §7 is flagged for rewording in Section 10 to match.

- Latch cleared while the episode is open (decided): if frames show mandown back at 0 (jacket CANCEL) while the episode is OPEN or ACKNOWLEDGED, the episode stays open and the card reads "Latch cleared on jacket (CANCEL SEEN): resolve with reason". An operator still has to Resolve; nothing is auto-resolved.

- Resolved while still latched (Proposed): if frames still show mandown=1 after Resolve, the responder keeps a persistent row "LATCH STILL SET ON JACKET" and the red hotspot, with no card and no sound, until the jacket CANCEL clears it. End shift lists it.

advisory_summaries. id PK; session_id INTEGER FK (NOT NULL); event_seq INTEGER NOT NULL (global sequence counter); ts, node_id; window_s (window the advice covers); risk, reasons, action (Tier 1 comes from the fixed advise(level, reasons) table; for source = table rows risk is CHECK-constrained to the six 14.3 labels, and action is the matching 14.3 text set in code, not separately validated, because Tier 2 and 3 sources write other values); source (table in Tier 1; Tier 2 or 3 sources are labelled advisory); passage_ids (Tier 3 retrieval only); quality (Spec): high = no fault and at least 80% of the window, medium = no fault and 50 to 80%, low = any fault or under 50%.
