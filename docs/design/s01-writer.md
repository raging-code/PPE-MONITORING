Commit-before-broadcast & bounded write durability (Proposed, rewritten Rev 3.27). The frame row, the alert rows it raises, and any episode change commit in one SQLite transaction BEFORE WebSocket broadcast, waiting up to commit_wait_ms = 120 ms for writer confirmation. All writes go through ONE bounded ordered writer queue (max 500 units); there is no priority or low-priority lane and no separate RAM retry buffer (2.10). event_seq is allocated on the host event loop when a unit is enqueued, and units commit strictly in event_seq order, so frame_id and episode_id foreign keys always exist before dependent rows. If the writer is blocked or a commit exceeds commit_wait_ms = 120 ms (a transient fault: disk or antivirus stall, database busy or locked, disk I/O error or disk full), the unit stays at the head of the queue and is retried in place, LOGGING FAULT is raised in active system state, and ANY alert (DANGER or WARNING) broadcast before SQLite commit carries unpersisted=1 (flagged in the UI until persisted, resolving the section 1 vs. 3.7 contradiction). If the queue is full, the oldest queued diagnostic/routine frame units are dropped first (alert-raising and episode-mutating units are kept) and counted in retry_buffer_dropped in COUNTERS (the counter name is kept so existing tests still apply). Normal WAL commits are expected to take a few ms at 1.5 frames/s, but this is UNMEASURED until the 2.10 benchmark runs. Watermark checkpoints are dormant in Tier 1 (2.10). On every restart, the host logs the exact count of any uncommitted gap in RECOVERING_ENTER and starts HOST_GAP at the timestamp of the last committed row rather than the restart timestamp. Deterministic failures (Rev 3.36, Proposed, confirm with the adviser): a commit that fails with a constraint error (sqlite3.IntegrityError: CHECK, FOREIGN KEY, UNIQUE, NOT NULL, or the trg_frames_roster abort) or a binding error (DataError, ProgrammingError, InterfaceError) fails again if retried, so it is never retried in place and never blocks the queue. The host rolls the unit back and commits its rows one by one, each in its own transaction and in the original order; a row that commits is kept, and an alert row whose frame row was rejected is written with frame_id NULL. A rejected row is skipped and counted in write_rejected in COUNTERS, and one LOGGING_FAULT system event per distinct SQLite message per minute records the table and the message. LOGGING FAULT is raised as for any write error and clears on the next unit that commits without a rejected row. If the skipped row was an alert or an episode change, the alert stays in live host state with unpersisted=1 and the host alarm keeps sounding until its condition clears or the host restarts; over-alarming is accepted on this path, which exists only as a backstop for a host bug. The next unit then commits normally.
